# A5. Distill a student

**Goal:** train a small model, Qwen 4B, on the labels Qwen 235B wrote in A4, and score it against Jev.

| | |
|---|---|
| Where | Marlowe: 1 H100 per job |
| Data | 5,000 training filings with Qwen 235B's labels, then 1,000 test filings to score |
| Teacher | Qwen 235B, from A4 |
| Student | [Qwen3.5-4B-Base](https://huggingface.co/Qwen/Qwen3.5-4B-Base), trained as a LoRA |
| Before you start | [Step 5 in A4]({{ '/advanced/a4/' | relative_url }}#step-5-label-at-scale) |

Qwen 235B needs a whole node of 8 H100s to run. A model with 4 billion parameters fits on one GPU, or on a laptop,
and answers many times faster. In this task you train such a small model to answer like Qwen 235B.

### Fine-tuning and distillation

Fine-tuning is a method, and distillation is one use of it.

- **Fine-tuning** takes a model that is already trained and keeps training it on labelled examples, so it gets better
  at a task. The labels can come from anywhere: people, a database, or another model.
- **Distillation** is fine-tuning where the labels come from another model, usually a much larger one, and the goal is
  for the small model to give the large one's answers. The large model is the *teacher*, the small one the *student*.
  You pay for the teacher once, to label the training data, and then run the cheap student.

Here the student is a LoRA on Qwen3.5-4B, fine-tuned on Qwen 235B's answers. The training is ordinary fine-tuning.
What makes it distillation is that the labels come from a larger model, and the goal is a small model that can stand
in for it.

In classic distillation, the student learns from the teacher's probabilities, which carry how sure the teacher was as
well as its choice. A model that outputs its answer as tokens, such as Qwen 235B, can report these probabilities too,
for every token it outputs. In this example, we keep only Qwen 235B's answers, so the student learns from its choices alone.

## Step 2: Make the training data

In distillation, the teacher's answers are what the student learns from. For each training filing, the teacher's
answer to each question becomes the student's *target*, the answer it should learn to give. Training shows the
student the filing, compares its answer with the target, and adjusts the student's weights a little, then moves on to
the next filing. Here the student is a LoRA, so only the weights of its small adapter change, along with a small
scoring layer described below; the base model's weights stay as they are:

Both models end in a *head*, the layer that turns the model's numbers into probabilities. The two heads differ:

- The teacher, Qwen 235B, has the usual head of a language model.
  - At each step it gives a probability for every token it knows, and one token is output.
  - At the answer, structured outputs allow only an option number, or true or false. vLLM outputs the most likely of
    these, so one choice comes out.
  - The probabilities behind that choice come back only when the request asks for them, and ours does not.
- The student, Qwen3.5-4B, has that head replaced by a small new one that scores the options directly.
  - In the prompt, each option ends with a marker token, and each question ends with a decision token.
  - For each option, the head compares the model's numbers at the option's marker with its numbers at the decision
    token, and gives the option a score.
  - A softmax turns the scores into a probability for each option. The probabilities add up to 1, and the student's
    answer is the most likely option.
  - The new head starts untrained and learns along with the LoRA weights.

Each target here is the teacher's one choice per question, so the student learns what to answer but not how sure to
be. A target like this, with all its weight on one option, is called a *hard label*.

## Step 3: Train the student

Train the student on the teacher's labels, on one H100:

```bash
sbatch --reservation=hackathon slurm/marlowe/advanced/a5_train_student.slurm qwen-235b
```
{: .marlowe }

The argument names the teacher: the job trains on `$WORK/data/teacher-<teacher>.jsonl` and saves the student in
`$WORK/runs/a5-<teacher>`. The job takes about 15 minutes. Follow its log:

```bash
tail -f logs/a5-student-<jobid>.out
```
{: .marlowe data-job-label="Student job ID" }

The training settings, chosen for a 4B model:

- **A LoRA**, rank 16, on Qwen3.5-4B-Base. The base model's weights stay as they are, and a small adapter and the
  pointer head, which scores the options, learn.
- **Learning rate 5e-5**, and 16 filings per optimizer step.
- **100 optimizer steps**, so 1,600 of the filings, to fit the session. The full recipe trains for two epochs, so
  the student sees each of the 5,000 filings twice; that takes about an hour on one H100.

Open `slurm/marlowe/advanced/a5_train_student.slurm` to see the full command.

## Step 4: Score the student

When the student is trained, label the 1,000 test filings with it. `serve_and_label.slurm` serves the model on one H100,
sends it the filings, and scores the answers against Jev's:

```bash
sbatch --reservation=hackathon slurm/marlowe/serve_and_label.slurm $WORK/runs/a5-qwen-235b a5-qwen-235b
```
{: .marlowe }

The first argument is the model, the second the name of its answers file in `$WORK/results/`. For a model to compare
with, score Kev-4B as released, which is the job's default:

```bash
sbatch --reservation=hackathon slurm/marlowe/serve_and_label.slurm
```
{: .marlowe }

It saves `$WORK/results/kev-4b-zeroshot.jsonl`. When the jobs have finished, put every model side by side, the teacher
from A4 included:

```bash
$PY scripts/score.py \
  $WORK/results/qwen-235b.jsonl \
  $WORK/results/a5-qwen-235b.jsonl \
  $WORK/results/kev-4b-zeroshot.jsonl
```
{: .marlowe }

`score.py` prints one row per model.

<details markdown="1">
<summary>Ideas to explore</summary>

- How close does the student come to its teacher? Where it disagrees with Qwen 235B, which of the two agrees with Jev?
- How does the student compare with Kev-4B, which was trained on other data, not on these filings?
- What did the teacher's labels cost in GPU-hours (A4), and what did the student's training cost? How many filings
  would the student have to label before it paid for itself?
- Could the student learn how sure to be? vLLM can return each written token's probabilities (`logprobs` and
  `top_logprobs` in the request). The options are numbered, so the probabilities of the digits where the teacher
  outputs its answer are a probability for each option. Ask for them in `label.py`, turn them into targets in
  `make_teacher_data.py`, and train a second student on them.
- Would more training help? Remove `--max_steps 100` and set `--epochs 2` in the job file for the full recipe,
  and give the job `--time=01:30:00`. A4 Step 5 can also label more filings with Qwen 235B.
