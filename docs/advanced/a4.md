# A4. Inference at scale

**Goal:** serve Qwen 235B across all 8 H100s of one Marlowe node, time how long it takes to load, then label filings
with it and measure how many it answers per second.

| | |
|---|---|
| Where | Marlowe: 1 node, 8 H100s |
| Data | 1,000 test filings with Jev's labels, then 5,000 training filings |
| Model | [Qwen 235B](https://huggingface.co/Qwen/Qwen3-235B-A22B-Instruct-2507-FP8) |
| Server | [vLLM](https://docs.vllm.ai), in an Apptainer container |
| Before you start | [Step 1 in A2]({{ '/advanced/a2/' | relative_url }}#step-1-set-up-on-marlowe) |

The work is split across two machines, as in [A1]({{ '/advanced/a1/' | relative_url }}). A Slurm job on a GPU node runs
the server and stays up. From the login node, you send it the filings and score its answers.

## Step 2: Start the server

Qwen 235B's weights are 237 GB, three times one H100's 80 GB, so the server splits the model across all 8 GPUs.
vLLM does this with **tensor parallelism**: every layer of the model is cut into 8 pieces, one per GPU, and the GPUs
compute each layer together, exchanging partial results over NVLink. A2's FSDP also shares a model across GPUs, but
for training: there, each GPU keeps a slice of the weights and borrows the rest when it needs them.

Qwen 235B is a *mixture of experts*. Each of its 94 layers holds 128 small sub-networks, the experts, and a router
that sends each token through 8 of them. The router is a small layer, trained along with the rest of the model, that
gives every expert a score for the token in front of it. The 8 experts with the highest scores process the token, and
their outputs are added up, each weighted by its score. A different token, or the same word in a different context,
can go to a different 8. Every token also goes through the parts all tokens share, such as attention.
Altogether, a token uses about 22 billion of the 235 billion parameters: the "A22B" in the model's full name means
22 billion active. All 235 billion must sit in GPU memory, which is why the server needs 8 H100s, but each token takes
the compute of a 22-billion-parameter model, so it answers much faster than its size suggests.

```bash
mkdir -p logs
sbatch --reservation=hackathon slurm/marlowe/advanced/a4_serve_qwen235b.slurm
```
{: .marlowe }


The job takes a whole node, starts vLLM in its container, and serves until you stop it or it reaches its 1-hour
limit. It writes its address to `$WORK/qwen-235b.server`:

```bash

```

the GPUs to answer fast and sets aside memory for the requests it will serve.

<details markdown="1" id="kv-cache" open>
<summary>While you wait: the KV cache</summary>

Qwen 235B writes its answer one token at a time; a token is a word or a piece of a word. To write each token, the
model looks back at every token before it: the filing and the questions in the prompt, and the answer so far. This
step is called *attention*.

Every layer of the model does attention, and each layer computes two sets of numbers for every token: a *key*, which later tokens match against to
find the tokens that matter to them, and a *value*, the information the token passes on when it matters. A token's keys
and values never change, so vLLM computes them once, in every layer, and keeps them in GPU memory, adding one more entry each time the
model writes a token. That store is the *KV cache*. Without it, the model would reprocess the whole filing for every
token of its reply.

The cache takes a lot of memory, because it holds every layer's keys and values for every token: for Qwen 235B, about
190 KB per token, or about 400 MB for a filing of 2,000 tokens.

vLLM sets the cache aside when it starts. Each H100 has 80 GB of memory, and vLLM claims 90% of it by default, then
divides that up in order:

1. Its share of the weights: with 8 GPUs, an eighth of the model's 237 GB, about 30 GB.
2. Working space for the computation, a few GB, which vLLM measures by running a test batch.
3. Everything left over becomes the KV cache.

So a GPU holds both the model and the requests in progress, and the more of its memory the weights take, the fewer
filings it can work on at once. This is also why `nvidia-smi` shows each GPU's memory nearly full even when no
requests are coming in. The log reports the cache's size:

```bash
grep -E "GPU KV cache size|Maximum concurrency" logs/a4-qwen235b-server-<jobid>.out
```
{: .marlowe }

The first line is how many tokens fit, across all requests at once. The second is how many requests fit at once if
each were as long as the server allows, 16,384 tokens. That is a lower bound: a filing with its questions is only a
few thousand tokens, so many more filings fit. Divide the first number by the length of a filing to estimate how
many.

When the cache is full, new requests wait until a running one finishes and frees its space. Keep this in mind in
Step 5, when you raise `--concurrency`.

</details>

#### What happens to each filing

Here `scripts/label.py` talks to vLLM, which serves Qwen 235B. In pseudocode:

<pre class="pseudo"><span class="pc"># scripts/label.py --api chat: on the login node</span>
<span class="pk">for each</span> filing, --concurrency at a time:
    <span class="pv">prompt</span> = the filing + the questions, each with numbered options
    <span class="pv">schema</span> = the Answers class as a JSON schema: status 1 to 8, why 1 to 8, future true or false
    send {prompt, schema, temperature 0, max 64 tokens} to vLLM (/v1/chat/completions)
    turn the numbers in the reply back into the options they stand for
    write {id, ok, seconds, answers} as one line of the --out file

<span class="pc"># vLLM: on the 8 H100s</span>
<span class="pk">keep</span> every waiting request in one queue; at each step, run all of them on the GPUs together
<span class="pk">for each</span> request:
    read the prompt: one forward pass over its tokens
    write the reply token by token, allowing only tokens that keep the JSON valid
    <span class="pk">stop when</span> the JSON is complete</pre>

This is the difference from Kev in A1. Kev reads a filing once and scores the options, so it returns a probability
for every option. Qwen 235B writes its answer out, token by token. vLLM can report the probabilities of each token it writes, but
`label.py` does not ask for them: it records only the choice Qwen 235B wrote, and `noul` is 1 or 0. `temperature 0` makes it pick the most likely token every time,
so if you label a filing again, you usually get the same answer, but not always. The server's arithmetic can come out
very slightly different from run to run, depending on which other filings it is working on at the same time. When the
model is torn between two options, that small difference can change its answer.

{: .tip }
> If anything in the code is unclear, ask Claude Code or Codex about it.


`--api chat` in the command above tells `label.py` which kind of server it is talking to. `chat` means a server that
answers chat messages through `/v1/chat/completions`, the interface vLLM and most model servers offer. With
`--api chat`, each filing becomes one request to vLLM, in three parts.

1\. One prompt. `label.py` puts the filing and Jev's three questions in a single message. Each question is headed by
the name of its field in the reply, and its options are numbered. Here is the whole prompt for one test filing;
scroll inside the box to read it all:

```
CNA FINANCIAL CORP
Form 8-K filed 2024-06-05, Item 5.02

On June 5, 2024, the Registrant issued a press release announcing that, following the end of his current term in the role of Chief Executive Officer and Chairman of the Board of Directors of the Registrant on December 31, 2024, Dino E. Robusto will transition to a new role with the Registrant. Mr. Robusto was appointed Executive Chairman of the Board of Directors of the Registrant effective January 1, 2025 and will remain employed by the Registrant in such role, serving as Executive Chairman of the Board and a strategic advisor to the Chief Executive Officer for a term of one year, ending on December 31, 2025. The press release is filed as Exhibit 99.1 to this Form 8-K.

---

Answer three questions about the filing above.

status: What happens to the company's chief executive officer, according to this filing?
1. the CEO is not leaving the CEO position (the filing is about someone else)
2. the CEO is stepping away temporarily (medical or other leave) and is expected to return
3. the CEO gives up the CEO title and becomes executive chair
4. the CEO gives up the CEO title and becomes non-executive (independent) chair
5. the CEO gives up the CEO title and stays only as a board member (not chair)
6. the CEO gives up the CEO title but stays at the company in another executive or advisory role
7. the CEO is leaving the company entirely (including death)
8. an interim or acting CEO is stepping aside for a permanent one

why: If the chief executive is leaving the CEO position, why, according to this filing? Judge only from what the filing says.
1. the departing CEO died in office
2. the departing CEO left because of illness
3. the departing CEO was pushed out over job performance
4. the departing CEO was dismissed over legal or policy violations
5. the departing CEO retired voluntarily
6. the departing CEO left for a new job or venture
7. other: interim CEO stepping aside, merger or acquisition, company closed, or not a real turnover
8. the filing gives no reason for the departure

future: Does the change to the CEO position take effect at a future date (announced in advance), rather than immediately or already?
```
{: .prompt }

2\. Structured outputs. The prompt never asks for JSON. Instead, `label.py` describes the reply as a Pydantic
model:

```python
class Answers(BaseModel):
    model_config = ConfigDict(extra="forbid")   # no other fields
    status: Literal[tuple(STATUS)]              # an option number, 1 to 8
    why: Literal[tuple(REASON)]                 # an option number, 1 to 8
    future: bool                                # true or false
```
{: .python-file }

Pydantic turns the class into a JSON schema, `Answers.model_json_schema()`, which goes with the request. vLLM
enforces it as the model writes, allowing at each step only the tokens that keep the reply valid. The model cannot
answer in prose, invent an option, or break the JSON. Every reply looks like
`{"status": 7, "why": 5, "future": false}`.

3\. Back to the options. `label.py` reads the reply with `Answers.model_validate_json` and turns the numbers back into
the options they stand for, 7 into "the CEO is leaving the company entirely". Then it saves the line in the
`--out` file.

<details markdown="1" id="structured-outputs">
<summary>Structured outputs: how vLLM holds the reply to the schema</summary>

A model that writes its answer picks one token at a time from its whole vocabulary, about 150,000 tokens for Qwen
235B. Nothing in that stops it from writing "The CEO is retiring." instead of `{"status": 7, ...}`, from choosing
option 9, or from leaving out a closing brace. Asking for JSON in the prompt makes those mistakes rarer, but over
thousands of filings a few still happen, and each one is a filing your script cannot read.

Structured outputs removes them, in four steps:

1. You describe the reply. Here that is the Pydantic class `Answers` in `scripts/label.py`, shown above.
   `Answers.model_json_schema()` turns it into this JSON schema:

   ```json
   {
     "additionalProperties": false,
     "properties": {
       "status": {"enum": [1, 2, 3, 4, 5, 6, 7, 8], "title": "Status", "type": "integer"},
       "why": {"enum": [1, 2, 3, 4, 5, 6, 7, 8], "title": "Why", "type": "integer"},
       "future": {"title": "Future", "type": "boolean"}
     },
     "required": ["status", "why", "future"],
     "title": "Answers",
     "type": "object"
   }
   ```
   {: .output }

   The class and the schema are the same rules in two forms: the class for Python, the schema for vLLM, which
   never sees the Python code.

2. The schema goes with the request, as its `response_format`.
3. vLLM turns the schema into rules for which token may come next. At each step, before the model picks, vLLM sets
   the probability of every token that would break the rules to zero. After `{"status": `, only the digits 1 to 8
   are left. The model still makes the choice, but only among valid tokens.
4. The reply is valid JSON that fits the schema, every time, and `Answers.model_validate_json` reads it into a
   Python object.

Two limits to keep in mind:

- The schema controls the form, not the content. It guarantees that `status` is a number from 1 to 8, not that it is
  the right number. Scoring against Jev's labels checks the content.
- The model never sees the schema: vLLM uses it only to block tokens. The prompt still has to say what each field
  means, which is why each question in the prompt is headed by its field name, `status`, `why` or `future`.

Most model servers and hosted APIs offer structured outputs, and many accept a Pydantic class directly, so the same
`Answers` class works with them too.

</details>

## Step 5: Label at scale

Now label training filings, as you would to make a teacher's labels for [A5]({{ '/advanced/a5/' | relative_url }}).
`--concurrency` is how many filings `label.py` keeps in flight at once; vLLM batches them on the GPUs. Name each run
with `RUN`, as in the A2 challenge. This first one, `a4-c64`, is the one A5 uses:

```bash
RUN=a4-c64
$PY scripts/label.py \
  --api chat \
  --model qwen-235b \
  --url http://$(cat $WORK/qwen-235b.server) \
  --data $WORK/data/train.jsonl \
  --limit 5000 \
  --concurrency 64 \
  --out $WORK/results/$RUN.jsonl \
  | tee $WORK/results/$RUN.log
```
{: .marlowe }

It prints the filings per second as it goes, and a summary at the end; 5,000 filings take a few minutes. Then try
other values of `--concurrency`, one run at a time, each with its own `RUN`: `a4-c128`, `a4-c256`, and so on. A run
whose `--out` file already has answers skips those filings, so a new value needs a new name. For example:

```bash
RUN=a4-c128
$PY scripts/label.py \
  --api chat \
  --model qwen-235b \
  --url http://$(cat $WORK/qwen-235b.server) \
  --data $WORK/data/train.jsonl \
  --limit 5000 \
  --concurrency 128 \
  --out $WORK/results/$RUN.jsonl \
  | tee $WORK/results/$RUN.log
```
{: .marlowe }

Compare `filings_per_second` in the summaries of your runs. At first, a higher concurrency makes the run faster,
because the GPUs get more filings to work on at once. At some point it stops helping: the GPUs are busy all the
time, and the extra filings only wait in vLLM's queue, so `latency_p50` goes up and the rate stays the same. At what
concurrency does that happen for Qwen 235B on 8 H100s?

#### Watch the GPUs

While the server is running, you can log in to its node and watch the GPUs live. Open a second terminal on the login
node, and while a `label.py` run is going:

```bash
ssh $(cut -d: -f1 $WORK/qwen-235b.server)
watch nvidia-smi
```
{: .marlowe }

`$WORK/qwen-235b.server` holds `node:port`, and `cut` keeps the node's name. Marlowe lets you log in to a node only
while you have a job on it. `watch` reruns `nvidia-smi` every 2 seconds. During a run, all 8 GPUs should be at or near
100% in the `GPU-Util` column:

![nvidia-smi on the server's node during a run: 8 H100s, each at 100% GPU-Util with about 77 GB of 80 GB in use, and one vLLM worker process per GPU]({{ '/assets/images/a4-nvidia-smi.png' | relative_url }})

`Memory-Usage` stays near full even between runs: vLLM takes most of each GPU's memory when it starts, for the weights
and for the requests it holds at once. Each GPU has one process, `VLLM::Worker_TP0` to `TP7`, one per piece of the
model. Press Ctrl-C to stop `watch`, and `exit` to go back to the login node.

When the runs are done, `gpu_util.py` reads the server's GPU log:

```bash
$PY scripts/gpu_util.py logs/gpu-<jobid>.csv
```
{: .marlowe }

The average covers the whole job, including the load and the minutes when no requests came in, so it is lower than
the use while a run was going. `logs/gpu-<jobid>.csv` has one line per GPU every few seconds, if you want to look at
one run.

## Optional challenge: label it faster

How many filings per second can you get from Qwen 235B on one node, without lowering its scores from Step 4? Some
changes that speed it up, such as a different prompt, also change what the model answers. So measure every attempt
on the same 1,000 test filings, and run `score.py` on each to check the scores as well as the speed. Change one thing
at a time, so you know what made the difference.

Step 5 found the concurrency where the rate stops growing; this challenge is about everything else. Use that
concurrency for every attempt. Name each attempt with `RUN`, as in the A2 challenge, and start with `a4-try0`, a run
with nothing changed, so every later attempt has a speed to compare with. For example, with your concurrency from
Step 5 in place of 64:

```bash
RUN=a4-try0
$PY scripts/label.py \
```

<details markdown="1">
<summary>Hints</summary>

You can change the client, `scripts/label.py`, or the server, the job file. A change to the client needs only a new
`label.py` run. A change to the server needs a new server job, which takes the node and several minutes to start.

- The order of the prompt. vLLM keeps the KV cache of a prompt's beginning and reuses it for the next prompt
  that starts with the same tokens. This is called *prefix caching*, and it is on by default. In `chat_prompt` in
  `label.py`, the filing comes first, so no two prompts start the same way. What happens if the questions come
  first? Check the scores too: the model reads the same words in a different order.
- The reply. The model writes the reply one token at a time, and each token is a step on the GPUs. How many
  tokens is a reply? Could the field names in `Answers` be shorter, and would the model still know what they mean?
- The server. Options for `vllm serve` go in `VLLM_ARGS`, in front of `sbatch`:

  ```bash
  VLLM_ARGS="--enable-expert-parallel" sbatch --reservation=hackathon slurm/marlowe/advanced/a4_serve_qwen235b.slurm
  ```
  {: .marlowe }

  Some to try: `--enable-expert-parallel` puts whole experts on each GPU instead of splitting every expert across
  all 8; `--max-num-seqs` sets how many requests vLLM runs in one step; `--data-parallel-size 2
  --tensor-parallel-size 4` runs two copies of the model, each on 4 GPUs. Does a copy fit in 4 GPUs, and how much
  KV cache is left? The log tells you.

</details>
