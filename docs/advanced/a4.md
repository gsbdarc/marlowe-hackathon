# A4. Inference at scale with Qwen 235B

**Goal:** serve Qwen 235B across all 8 H100s of one Marlowe node, time how long it takes to load, then label filings
with it and measure how many it answers per second.

| | |
|---|---|
| Where | Marlowe: the server on the 8 H100s of one node, the queries from the login node |
| Data | the 1,000 test filings with Jev's labels, then training filings (no labels needed) |
| Model | [Qwen3-235B-A22B-Instruct-2507-FP8](https://huggingface.co/Qwen/Qwen3-235B-A22B-Instruct-2507-FP8): 235 billion parameters in FP8, 237 GB of weights |
| Server | [vLLM](https://docs.vllm.ai) 0.31.0, in an Apptainer container |
| Before you start | [A2]({{ '/advanced/a2/' | relative_url }}) Step 1: your clone, Kev and the data on Marlowe |

The work is split across two machines, as in [A1]({{ '/advanced/a1/' | relative_url }}). A Slurm job on a GPU node runs
the server and stays up. From the login node, you send it the filings and score its answers.

## Step 1: Get ready

```bash
ssh <sunet>@login.marlowe.stanford.edu

source env/marlowe.sh
```
{: .marlowe }

Have Slurm email you when the job starts, ends or fails. Open the job file in an editor:

```bash
vi slurm/marlowe/advanced/a4_serve_qwen235b.slurm
```
{: .marlowe }

Find the `#SBATCH --mail-user` line near the top and put your Stanford email address in place of the placeholder, so
it reads:

```
#SBATCH --mail-user=<sunet>@stanford.edu
```
{: .output }

Save the file.

## Step 2: Start the server

Qwen 235B's weights are 237 GB, three times one H100's 80 GB, so the server splits the model across all 8 GPUs.
vLLM does this with **tensor parallelism**: every layer of the model is cut into 8 pieces, one per GPU, and the GPUs
compute each layer together, exchanging partial results over NVLink. A2's FSDP also shares a model across GPUs, but
for training: there, each GPU keeps a slice of the weights and borrows the rest when it needs them.

The model is a *mixture of experts*: each layer holds many small expert networks, and each word it reads goes through
only a few of them, 22 billion of the 235 billion parameters. That makes it much faster to run than its size suggests.

```bash
mkdir -p logs
sbatch slurm/marlowe/advanced/a4_serve_qwen235b.slurm
```
{: .marlowe }

The job takes a whole node, starts vLLM in its container, and serves until you stop it or it reaches its 2-hour
limit. It writes its address to `$WORK/qwen-235b.server`:

```bash
cat $WORK/qwen-235b.server
```
{: .marlowe }

## Step 3: Time the load

Follow the log:

```bash
tail -f logs/a4-qwen235b-server-<jobid>.out
```
{: .marlowe }

Every line starts with the minutes and seconds since the job began. vLLM reads the weights from the shared cache onto
the 8 GPUs, sets up its memory for requests, and then reports that the application has started. Find those moments:

```bash
grep -E "Loading weights took|Model loading took|startup complete" logs/a4-qwen235b-server-<jobid>.out
```
{: .marlowe }

How long did the weights take to load, and how long until the server was ready? When it is ready, it answers:

```bash
curl http://$(cat $WORK/qwen-235b.server)/v1/models
```
{: .marlowe }

Until then `curl` reports `Connection refused`.

{: .warning }
> The server has no authentication, and anyone on Marlowe can reach its port. Send it only the public filings in this
> task, and stop it when you are done.

## Step 4: Label the test filings and score them

Send the 1,000 test filings from the login node:

```bash
$PY scripts/label.py --api chat --model qwen-235b --url http://$(cat $WORK/qwen-235b.server) \
  --data $WORK/data/test1000.jsonl --out $WORK/results/qwen-235b.jsonl
```
{: .marlowe }

With `--api chat`, `label.py` writes the filing and Jev's three questions as one prompt with numbered options, and
asks vLLM for a JSON answer limited to those options. Then score the answers against Jev's:

```bash
$PY scripts/score.py $WORK/results/qwen-235b.jsonl
```
{: .marlowe }

Kev-27B was trained to answer questions like Jev's; Qwen 235B was not. Compare its scores with Kev-27B's from A1.

## Step 5: Label at scale

Now label training filings, as you would to make a teacher's labels for [A5]({{ '/advanced/a5/' | relative_url }}).
`--concurrency` is how many filings `label.py` keeps in flight at once; vLLM batches them on the GPUs:

```bash
$PY scripts/label.py --api chat --model qwen-235b --url http://$(cat $WORK/qwen-235b.server) \
  --data $WORK/data/train.jsonl --limit 5000 --concurrency 64 --out $WORK/results/qwen-235b-train.jsonl
```
{: .marlowe }

It prints the filings per second as it goes, and a summary at the end. Try other values of `--concurrency`, each into
its own `--out` file: where does the rate stop growing? Watch the GPUs in `logs/gpu-<jobid>.csv` as you do.

Stop the server, so the node is free for the next person:

```bash

```
