# A2. Fine-tune Qwen 27B

**Goal:** fine-tune Qwen3.8-27B on Jev's labels on one H100, then on all 8 H100s of one Marlowe node, and compare
what each needs.

| | |
|---|---|
| Where | Marlowe: 1 H100, then the 8 H100s of one node |
| Data | 54,426 filings (2004 to 2018) with Jev's labels |
| Model | [Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B), 27 billion parameters |
| Trainer | Kev's trainer: a full fine-tune, which trains every weight of the model |

Both jobs run the same training: 100 optimizer steps of 16 filings each, so their times compare. A3 runs it again on
two nodes.

In plain terms, one optimizer step:

1. **Read.** The model reads a filing, one question and its options. The pointer head, the small new part on top of
   the model, gives each option a score.
2. **Guess.** Softmax turns the scores into probabilities that add up to 1: Kev's guess.
3. **Compare.** The loss is a single number for how far Kev's guess is from Jev's probabilities. A perfect match would
   give the lowest possible loss.
4. **Work out the nudge.** Going backward from the loss, the trainer works out, for each of the 27 billion weights,
   which way and how much to nudge it to make the loss smaller. That is the weight's gradient.
5. **Nudge.** After 16 filings, with their gradients added up, the optimizer moves every weight a small step in its
   direction. That is one optimizer step.

In pseudocode, for the one-GPU job: the outer loop is the 100 optimizer steps, and the inner loop is the passes that
make up one step. One step trains `BATCH` × `ACCUM` = 1 × 16 = 16 filings.

#### BATCH and ACCUM

- `BATCH` is how many filings the GPU reads at the same time, in one pass.
- `ACCUM`, short for gradient accumulation, is how many passes it runs before it updates the weights, adding up
  the gradients of each pass.

Two ways to train 16 filings per update:

| | `BATCH` = 1, `ACCUM` = 16 (this job) | `BATCH` = 16, `ACCUM` = 1 |
|---|---|---|
| Filings in each pass | 1 | 16 |
| Passes before the weights update | 16 | 1 |
| Filings per update | 16 | 16 |
| Memory for the intermediate results of a pass | one filing's | 16 filings' |
| Speed | slower: 16 small passes | usually faster, if it fits in memory |
{: .plain-head }

Either way, each update learns from the same 16 filings. The difference is memory and speed.

<pre class="pseudo"><span class="pc"># kev/train.py, on one GPU</span>
<span class="pv">model</span> = Qwen3.8-27B, plus a new pointer head that starts from random weights
<span class="pv">filings</span> = train.jsonl, less the filings too long to train on
<span class="pv">optimizer</span> = AdamW: learning rate 2e-6 for the model, 1e-4 for the new head

<span class="pk">for</span> step in 1 to 100:                          <span class="pc"># the 100 optimizer steps</span>
    <span class="pk">for</span> pass in 1 to 16:                       <span class="pc"># ACCUM = 16 passes make up one step</span>
        take the next filing                   <span class="pc"># BATCH = 1</span>
        <span class="pv">loss</span> = 0
        <span class="pk">for each</span> question in that filing:
            <span class="pv">scores</span> = run the model, then the pointer head scores each option
            <span class="pv">loss</span> = loss + cross-entropy of softmax(scores) against Jev&#x27;s probabilities
        backward(loss)                         <span class="pc"># added to the earlier passes&#x27; gradients</span>
    <span class="pc"># the gradients now add up over 16 filings</span>
    clip the gradients if they are too large
    update every weight a small step, using its gradient      <span class="pc"># the optimizer step</span>
    reset the gradients to zero
    <span class="pk">if</span> step is a multiple of 10: print the step, the loss and the seconds per filing

<span class="pk">save</span> the weights, the head, the tokenizer and training_metrics.json</pre>

- **The loss** measures how far the model's probabilities are from Jev's. Jev's labels are probabilities over the
  options, so the model learns how sure Jev was, not only Jev's answer. It is the `loss` the log prints every 10 steps.
- **The learning rate** sets how far each weight moves in one optimizer step. The learning rate starts small, rises
  over the first 10% of the steps, then falls again. Kev uses two learning rates: 1e-4 for the new pointer head and
  2e-6 for the rest of the model, so each step moves the head's weights about 50 times as far as Qwen's. The head
  starts from random numbers and has a long way to go; Qwen's weights already work and need only small adjustments.

### Checkpoints: saving the training to disk

A **checkpoint** is a copy of a training run's state, saved to disk, so that a new job can carry on where the old one
stopped. A job can stop partway for many reasons: it crashes, it reaches its time limit, or the scheduler preempts it
to make room for another job. Without a checkpoint, the next job starts again from the first step.

A checkpoint you can resume from holds more than the weights:

| What | Why |
|---|---|
| the model's weights | what training has learned so far |
| the optimizer state | AdamW keeps two running averages for every weight; without them, training does not continue the same way |
| the learning-rate schedule and the step | so the learning rate picks up where it was |
| the position in the data | so the next job does not train on the same examples again |

In plain PyTorch, saving and resuming look like this:

```python
# every so often during training
torch.save({"step": step, "model": model.state_dict(), "optimizer": optimizer.state_dict(),
            "scheduler": scheduler.state_dict()}, "/scratch/.../checkpoint.pt")

# at the start of the next job, if a checkpoint exists
ckpt = torch.load("/scratch/.../checkpoint.pt")
model.load_state_dict(ckpt["model"])
optimizer.load_state_dict(ckpt["optimizer"])
scheduler.load_state_dict(ckpt["scheduler"])
start_step = ckpt["step"] + 1
```

With the Hugging Face `Trainer`, it is a few settings:

```python
args = TrainingArguments(output_dir="/scratch/.../my-run", save_strategy="steps", save_steps=500,
                         save_total_limit=2)          # keep only the two newest checkpoints
trainer.train(resume_from_checkpoint=True)            # carry on from the newest checkpoint, if there is one
```

Things to decide whenever you train:

- **How often to save.** Writing a checkpoint takes time, and everything since the last one is lost if the job stops.
  Save often enough that losing the work since the last save is acceptable, and well before the job's time limit.
- **Where.** Checkpoints of large models are large: the weights and the optimizer state together take about 16 bytes
  per parameter, hundreds of GB for a 27-billion-parameter model. Write them to scratch, never your home directory,
  and keep only the newest few.
- **Across several GPUs.** When the model is split across GPUs, as with FSDP in Step 3, each GPU holds only its piece.
  PyTorch's distributed checkpointing (`torch.distributed.checkpoint`) has each GPU write its own piece at the same
  time.

**In these jobs.** Kev's trainer calls checkpoints resume points, and three `kev.train` options control them:

| Option | What it does |
|---|---|
| `--save_every_steps N` | writes a resume point to `<run folder>/resume` every N optimizer steps |
| `--save_every_minutes M` | writes one once M minutes have passed since the last |
| `--resume 1` | continues from `<run folder>/resume` if there is one, and starts from scratch if not |

The A2 jobs train for only 100 steps, a few minutes, so they save no resume points, only the finished model at the end.
Our job file also clears the run folder when it starts (`rm -rf "$OUT"`), so to resume a run you would remove that
line first.

{: .note }
> **Training other models.** None of this is specific to Kev. Most training libraries have the same two pieces: a
> setting for how often to save, and a way to resume. In the Hugging Face `Trainer` they are `save_steps` and
> `resume_from_checkpoint`; in PyTorch Lightning, the `ModelCheckpoint` callback and `trainer.fit(..., ckpt_path="last")`.
> Before a long run of any model, check that it saves checkpoints, stop a short test run and resume it once to see
> that resuming works, and make sure your job file does not delete the folder it resumes from.

## Step 3: Fine-tune on 8 H100s with FSDP

**FSDP**, Fully Sharded Data Parallel, is PyTorch's way of training one model on several GPUs at once:

- **Data parallel:** each GPU trains on different filings at the same time, and the GPUs combine their gradients
  before every optimizer step. Eight GPUs process eight filings at once.
- **Fully sharded:** no GPU holds the whole model. Each holds one eighth of the weights, one eighth of the gradients
  and one eighth of the optimizer state. When the model runs a layer, the GPUs pass each other their pieces of that
  layer, compute, and drop the borrowed pieces again. After the backward pass, each GPU keeps only the gradients for its
  own piece.

The price is communication: the GPUs exchange data at every layer. Inside one Marlowe node the 8 H100s are connected by
NVLink, which is fast enough that the exchange costs little. Kev's trainer uses FSDP2, the current version in PyTorch.
`torchrun` starts 8 copies of the trainer, one per GPU, and they find each other to share the work.

```bash
sbatch slurm/marlowe/advanced/a2_train_8gpu.slurm
```
{: .marlowe }

The training is the same loop as in [While it runs](#the-training-loop), run by 8 copies of the trainer at once.
Each update still trains 16 filings, as on one GPU. In one pass, the 8 GPUs read 8 filings at the same time, one each,
so 2 passes make the 16. What changes:

<pre class="pseudo">torchrun starts 8 copies of kev/train.py, one per GPU, numbered 0 to 7
each copy holds one eighth of the weights, gradients and optimizer state (FSDP)

<span class="pk">for</span> step in 1 to 100:                              <span class="pc"># the 100 optimizer steps</span>
    <span class="pk">for</span> pass in 1 to 2:                            <span class="pc"># 2 passes x 8 GPUs = 16 filings</span>
        each copy takes its own next filing        <span class="pc"># 8 filings at once</span>
        <span class="pk">for each</span> layer, forward and then backward:
            fetch the other seven pieces of that layer from the other GPUs (NVLink)
            compute, then drop the borrowed pieces
    combine the gradients: each copy keeps the total for its own eighth
    each copy updates its own eighth of the weights</pre>

The job takes a whole node, so it may wait in the queue longer than the one-GPU job. Follow its log:

```bash
tail -f logs/a2-27b-8gpu-<jobid>.out
```
{: .marlowe }

After a few minutes of loading, the trainer prints how it set up the run, then a line every 10 optimizer steps.

The time to the first `step` line is the model load; the time between step lines is the training.

`world=8` is the number of GPUs sharing the job. [Monitoring Training]({{ '/monitoring/' | relative_url }}) explains the
other fields. Compare the `memory.used` column of this job's `logs/gpu-<jobid>.csv` with the one-GPU job's.

## Step 4: Measure it

When the job prints `saved`, turn its step times into how long a full pass over the training data would take, and
how many GPU-hours it would use:

```bash
$PY scripts/step_times.py $WORK/runs/a2-8gpu
```
{: .marlowe }

It reads the run's `training_metrics.json` and prints one row:

| Column | What it means |
|---|---|
| `GPUs` | how many GPUs shared the training |
| `steps` | optimizer steps the run did; each step trains on 16 filings |
| `s/step` | seconds per step: the median step time, skipping the first 3, which are slower while things warm up |
| `peak GPU GB` | the most memory PyTorch used on any one GPU, out of an H100's 80 GB |
| `epoch hours` | how long one epoch, training on every filing once, would take at this speed |
| `epoch GPU-hours` | what that epoch costs: hours × GPUs. Use it to compare runs on different numbers of GPUs |

The run trained for only 100 steps, so the script projects the rest. It trains on 52,757 filings (the 54,426 in
`train.jsonl` less the 1,669 that are too long), so one epoch is 52,757 ÷ 16 = 3,297 steps. `epoch hours` is 3,297 ×
`s/step` ÷ 3,600, and `epoch GPU-hours` is that times the GPUs.

How busy were the GPUs? Each job writes a GPU log, `logs/gpu-<jobid>.csv`, with every GPU's utilization and memory
every 15 seconds. Sum up the logs of all your jobs:

```bash
$PY scripts/gpu_util.py logs/gpu-*.csv
```
{: .marlowe }

It prints one row per job:

| Column | What it means |
|---|---|
| `job` | the Slurm job ID |
| `GPUs` | how many GPUs the job used: 1 for the one-GPU job, 8 for this one |
| `average use` | the GPUs' utilization, averaged over the whole job |
| `peak use` | the highest utilization in any sample |
| `peak memory GB` | the most memory any one GPU held |

The peak use is close to 100% on almost any run. The average, which includes the minutes of loading and saving, is
the one to watch: a GPU waiting on data or on other GPUs is not training. `peak memory GB` is a little higher than
`step_times.py`'s `peak GPU GB`, because the GPU log also counts memory PyTorch has set aside but is not using.

## Optional challenge: train it faster

How would you make this run faster? Each attempt is the same 100-step job as your first 8-GPU run, about 15 minutes,
so aim for at least three attempts. Change one thing at a time, so you know what made the difference, and
keep going: try other settings, combine the ones that helped, and find where each one stops helping or runs out of
memory.

{: .note }
> Claude Code or Codex is fair game.

<details markdown="1">
<summary>Hints</summary>

Most attempts need no file edits. The job file builds its training command from a few variables in
`slurm/train_27b_args.sh`. Put them in front of `sbatch`, on the same line, and they apply to that run only:

| Variable | Default | What it changes |
|---|---|---|
| `RUN` | `a2-8gpu` | the run's name and its folder, `$WORK/runs/<RUN>` |
| `BATCH` | 1 | filings each GPU trains on in one forward and backward pass |
| `ACCUM` | 2 | passes before each weight update. The GPUs add up what they learn over these passes, then update the model once. Each update trains `BATCH` × `ACCUM` × 8 filings: 16 with the defaults |
| `EXTRA_ARGS` | none | any other `kev.train` option |

- Look at the GPU log of your first 8-GPU run: how much of each H100's 80 GB did it use, and how busy was each GPU?
- `BATCH=1 ACCUM=2` and `BATCH=2 ACCUM=1` both train 16 filings per update, so the training is the same. They differ
  in speed and memory. One bigger pass keeps each GPU busier and means fewer rounds of exchanging data between the
  GPUs, so it is usually faster, but it holds twice as many filings in memory at once. If that does not fit in the
  H100's 80 GB, the run stops with an out-of-memory error. Try it:

  ```bash
  RUN=a2-try1 BATCH=2 ACCUM=1 sbatch slurm/marlowe/advanced/a2_train_8gpu.slurm
  ```
- Filings in a pass are padded to the longest one. `--length_sort 1` groups filings of similar length, so less of each
  pass is padding:

  ```bash
  RUN=a2-try2 EXTRA_ARGS="--length_sort 1" sbatch slurm/marlowe/advanced/a2_train_8gpu.slurm
  ```
- A pass that does not fit runs out of memory, like the one-GPU job did.
- If you change the filings per step, pass `--per-step` to `step_times.py`. More filings per step can still train
  well, but it is no longer the same training as the first run.

</details>

Start each attempt like this, with your own settings in place of `NAME=value`. Give each attempt its own `RUN`
(`a2-try1`, `a2-try2`, ...): a run replaces the folder of the same name, `$WORK/runs/<RUN>`.

```bash
RUN=a2-try1 NAME=value sbatch slurm/marlowe/advanced/a2_train_8gpu.slurm
```
