# A3. Fine-tune on two nodes

**Goal:** run the A2 fine-tune across two full Marlowe nodes, 16 H100s, and compare its time per step with one node.

| | |
|---|---|
| Where | Marlowe: 2 nodes, 16 H100s |
| Data | 54,426 filings (2004 to 2018) with Jev's labels |
| Model | [Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B) |
| Trainer | Kev's trainer, the same full fine-tune as A2 |
| Before you start | [Step 1 in A2]({{ '/advanced/a2/' | relative_url }}#step-1-set-up-on-marlowe) and [Step 3 in A2]({{ '/advanced/a2/' | relative_url }}#step-3-fine-tune-on-8-h100s-with-fsdp) |

The training is the same as A2's: 100 optimizer steps of 16 filings each. With 16 GPUs, each step gives one filing
to each GPU at once, where 8 GPUs took two passes of 8.

## Step 2: Fine-tune on two nodes

```bash
sbatch --reservation=GSB_Hackathon slurm/marlowe/advanced/a3_train_2node.slurm
```
{: .marlowe }

The training is A2's loop (see [A2]({{ '/advanced/a2/' | relative_url }}#the-training-loop)), run by 16 copies of
Kev's trainer at once. What changes:

<pre class="pseudo"><span class="pk">on each node:</span> torchrun starts 8 copies of kev/train.py, one per GPU
the 16 copies contact the first node of the job, to find each other
each copy gets a number from 0 to 15, its rank: which share of the work is its own
each copy holds one sixteenth of the weights, gradients and optimizer state (FSDP)

<span class="pk">for</span> step in 1 to 100:                              <span class="pc"># the 100 optimizer steps</span>
    each copy: 1 pass (ACCUM = 1) of 1 filing, forward and backward
        <span class="pk">before each layer:</span> fetch the other fifteen pieces of that layer from the other GPUs
    combine the gradients across all 16 GPUs           <span class="pc"># NVLink in a node, InfiniBand between</span>
    each copy updates its own sixteenth of the weights</pre>

{: .tip }
> If anything in the code is unclear, ask Claude Code or Codex about it.



The job asks for two whole nodes, so it can wait in the queue longer than A2's. Slurm starts one copy of `torchrun`
on each node, and each starts 8 trainer processes, one per GPU. The 16 processes find each other through the first
node of the job and share the model 16 ways with FSDP.

Follow the log:

```bash
tail -f logs/a3-27b-2node-<jobid>.out
```
{: .marlowe data-job-label="Two-node job ID" }

Every line starts with the minutes and seconds since the job began. After the model loads, the trainer prints a line
every 10 optimizer steps; `world=16` in its first line is the 16 GPUs. Each node also writes its own GPU log,
`logs/gpu-<jobid>-<node>.csv`.

The run is also on W&B, in the **advanced-a3** project on [Marlowe-Hackathon on W&B](https://forge.coreweave.com/wandb/Marlowe-Hackathon), next to the LoRA run if you
train one. A2's [Your run on Weights & Biases]({{ '/advanced/a2/' | relative_url }}#your-run-on-weights--biases)
says what it shows.

## Step 3: Compare with one node

When the log prints `saved`, compare the two runs:

```bash
$PY scripts/step_times.py $WORK/runs/a2-8gpu $WORK/runs/a3-2node
```
{: .marlowe }

It prints, for each run, the GPUs, the seconds per optimizer step, the peak GPU memory, and the hours and GPU-hours one
epoch would take. Then see how busy the GPUs were on each job:

```bash
$PY scripts/advanced/gpu_util.py logs/gpu-*.csv
```
{: .marlowe }

It prints one row per job: the GPUs, their average and peak utilization, and the most memory any one GPU held. The
two-node job's two GPU logs, one per node, come out as one row of 16 GPUs. A2 Step 4 explains each column.

<details markdown="1">
<summary>After you compare: what the numbers mean</summary>

**Speedup.** Divide the one-node `s/step` by the two-node `s/step`. 2 would be perfect: twice the GPUs, half the
time. Expect close to 2, but not quite. With FSDP, the GPUs exchange each layer's weights before using it and the
gradients after. Inside one node the 8 H100s talk over NVLink; between nodes the traffic crosses InfiniBand, which is
slower. With 16 GPUs, every exchange crosses that link, so some of the time the second node saves goes to waiting.

**Memory.** Each GPU holds half as much of the model as on one node, so the peak memory per GPU drops. It does not
halve: each GPU still trains on one filing at a time, and the memory for that filing stays the same.

**Cost.** A run's cost is its GPU-hours: the number of GPUs times the hours they run, which is `epoch GPU-hours`.
Two nodes use twice as many GPUs as one node. If they also took exactly half the time, the cost would be the same. They take a
little more than half, so the same epoch uses a few more GPU-hours. For example, if 8 GPUs took 10 hours, that is 80
GPU-hours; if 16 GPUs took 5.5 hours, that is 88. The second node gets you the result sooner, for a little more
compute.

</details>

## Full fine-tuning and LoRA

A2 and A3 run a **full fine-tune**: every one of the model's 27 billion
weights changes. The other common way to fine-tune a large model is **LoRA** (low-rank adaptation), which leaves the
model's weights as they are and trains a small set of new ones next to them.

### How LoRA works

A layer of the model multiplies its input by a large matrix of weights, `W`. A full fine-tune changes `W` itself.
LoRA freezes `W` and learns a correction made of two thin matrices, `A` and `B`, whose product has the same shape as
`W`:

For example, one of Qwen3.8-27B's weight matrices, `up_proj`, holds 89 million weights. A rank-16 LoRA for it trains
about 360,000 numbers instead, 0.4% as many. Over the whole model, a LoRA usually trains less than 1% of the weights.

### Full fine-tune or LoRA?

| | Full fine-tune | LoRA |
|---|---|---|
| Weights trained | all of them | the adapters, usually under 1% |
| GPU memory | about 16 bytes per weight (weights, gradients, fp32 master copy, AdamW's two moments): hundreds of GB for 27B, spread over several GPUs with FSDP | about 2 bytes per weight for the frozen model, plus the small adapters and their optimizer state |
| What you save | a full copy of the model, 51 GB for 27B | the adapter only, often tens to hundreds of MB, loaded on top of the base model |
| How much it can change the model | as much as the data asks | less; often enough to teach a format or a task |

**Where to start.** Try a LoRA first: it needs far less memory, trains faster, and is often enough. If it falls short
and you have enough labelled data, try a full fine-tune next, and expect it to take many more GPU-hours.

### Customizing a LoRA

The same few settings come up in every library. With Hugging Face PEFT:

```python
from peft import LoraConfig, get_peft_model

config = LoraConfig(
    r=16,                 # rank: the width of A and B. Higher learns more and costs more; 8 to 64 is common
    lora_alpha=32,        # scales the correction; often set to 2 × r
    lora_dropout=0.05,    # randomly drops some of the adapter's input in training, against overfitting
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],   # which layers get an adapter
)
model = get_peft_model(model, config)
model.print_trainable_parameters()   # shows how few weights the LoRA trains
```

- **Rank (`r`)** is the main dial: more capacity and memory as it goes up.
- **Target modules** choose where the adapters go: the attention projections only, or the feed-forward layers too
  (`gate_proj`, `up_proj`, `down_proj`), which trains more weights and can learn more.
- **Learning rate** is usually 10 to 100 times higher for a LoRA than for a full fine-tune of the same model: the
  adapters start at zero and have far fewer weights to move.

**In these jobs.** A LoRA is what Kev's trainer does unless you pass `--full_ft 1`, as our jobs do. `--lora` sets the rank
(16 by default), and `--lora_targets` picks the layers: `all`, `dense`, `attn` (the attention projections) or `qv`
(two of them). Kev fixes `lora_alpha` at 2 × rank and `lora_dropout` at 0.05, in `kev/model.py`.

RCpedia's [Fine-Tuning Open Source Models](https://rcpedia.stanford.edu/blog/2025/11/07/fine-tuning-open-source-models/)
walks through a LoRA fine-tune end to end: Qwen3-8B with a rank-32 adapter, trained through Together AI's API, then
the adapter downloaded and served with vLLM. It also covers how rank, cost and accuracy trade off. Training through an
API sends your data to the provider, so it is not for restricted data.
