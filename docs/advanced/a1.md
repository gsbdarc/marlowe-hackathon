# A1. Score before training

**Goal:** serve Kev-27B on one Yens H200 and measure how often it agrees with Jev. That score is the baseline for a
model you fine-tune fully, after the workshop (see the end of A2).

| | |
|---|---|
| Where | Yens: the server on 1 H200, the queries from an interactive node |
| Data | the 1,000 test filings (2022 to 2026) with Jev's labels |
| Model | [Kev-27B](https://huggingface.co/jaredpalmer/kev-27b), 51 GB of weights, built on Qwen3.8-27B |

The work is split across two machines. A Slurm job on a GPU node runs the Kev server and stays up. From your
interactive Yen node, you send it the filings and score its answers.

{: .important }
> Kev-27B needs an H200. Its 51 GB of weights do not fit on an A40 (48 GB). The Yens have only two H200s, both on
> `yen-gpu4`, and both are reserved for this class, so everyone in the room shares them. Your server holds one for up
> to 30 minutes. Stop it with `scancel` as soon as you have your scores (Step 5), so the next person's job can start.


`setup_kev.sh` puts everything in `$KEV_HOME`, `/scratch/users/<sunet>/kev`:

- **uv**, in `bin/uv`. [uv](https://docs.astral.sh/uv/) installs Python and Python packages, much faster than pip.
  Neither the Yens nor Marlowe has it, so setup installs it first. uv downloads Python 3.13, which Kev needs, into
  `uv-python/`, and keeps the packages it downloads in `uv-cache/`.
- **Kev's code**, in `kev/`: a clone of the [Kev repository](https://github.com/jaredpalmer/kev).
- **Kev's Python environment**, in `kev/.venv`: Python 3.13 with PyTorch, Transformers and the rest of Kev's
  packages. uv builds it from Kev's lock file, `uv.lock`, which pins every package version, so everyone gets the same
  environment.

That is why paths such as `kev/kev/.venv/bin/python` name `kev` twice: the first is your install folder, the second
the Kev code inside it.

Jev's data is in `/scratch/shared/marlowe_hackathon/data/`, readable by everyone on the Yens. That folder and the
model cache are read only: you read from them and never write to them. Copy the test filings
into your own work folder, `$WORK`. `source env/yens.sh` set it; see where it is:


## Step 3: Wait until it is ready

If both H200s are busy, the job waits in the queue first; `squeue --me` shows `PD` until it starts. Once it runs,
loading 51 GB of weights onto the GPU takes about 3 minutes. Follow the log:

```bash
tail -f logs/kev27b-server-<jobid>.out
```
{: .yens data-job-label="Server job ID" }

When the model has loaded, the server answers on its address:

```bash
curl http://$(cat $WORK/kev-27b.server)/v1/models
```
{: .yens }

Until then `curl` reports `Connection refused`. Wait and try again.

{: .warning }

> filings in this task, and stop it when you are done.

## Step 4: Label and score from the interactive node

The commands in this step start with `$PY`. See what it stands for:

```bash
echo $PY
```
{: .yens }

```
/scratch/users/<sunet>/kev/kev/.venv/bin/python
```
{: .output }

`$PY` is the Python in Kev's environment, which `setup_kev.sh` installed; `source env/yens.sh` sets it. Every script
in this task runs with it, so everyone runs the same Python and the same package versions, whatever `python3` or conda
environment comes first on your `PATH`. You do not need to activate the environment first. If `echo $PY` prints an
empty line, you are in a new terminal: run `source env/yens.sh` again.

With the server ready, send it the 1,000 test filings from your interactive node:

```bash
$PY scripts/label.py \
  --url http://$(cat $WORK/kev-27b.server) \
  --data $WORK/data/test1000.jsonl \
  --out $WORK/results/kev-27b-zeroshot.jsonl \
  | tee $WORK/results/kev-27b-zeroshot.log
```
{: .yens }

#### What happens to each filing

Two programs do the work: `scripts/label.py` on your interactive node, and Kev's server on the H200. In pseudocode:

<pre class="pseudo"><span class="pc"># scripts/label.py: on your interactive node</span>
<span class="pk">for each</span> filing in test1000.jsonl, 16 at a time:
    <span class="pv">request</span> = the text of the filing, and the three questions with their options
    send the request to the Kev server (POST /v1/systemone)
    write {id, ok, seconds, answers} as one line of kev-27b-zeroshot.jsonl

<span class="pc"># Kev&#x27;s server (kev/serve.py, kev/model.py): on the H200</span>
<span class="pk">for each</span> group of requests waiting at the same moment:
    <span class="pv">tokens</span> = the filing, then each question and its options, with marker tokens between them
    run the model once over the tokens                      <span class="pc"># one forward pass, no text</span>
    <span class="pk">for each</span> question:
        score each option against the &quot;decide&quot; marker of the question   <span class="pc"># the pointer head</span>
        <span class="pv">probabilities</span> = softmax(scores)                     <span class="pc"># one per option, adding up to 1</span>
        <span class="pv">choice</span> = the option with the highest probability
        <span class="pv">confidence</span> = how far the top probability is above an even guess, from 0 to 1
    <span class="pk">return</span> choice, confidence and probabilities for each question</pre>

A yes-or-no question such as `future` has two options, false and true, and `noul` is the probability of true. Kev
never writes an answer out word by word: it reads the filing once and scores the options it was given. In A4 you will
see a model that writes its answer instead.

{: .tip }
> If anything in the code is unclear, ask Claude Code or Codex about it.


{: .note }
> Here you run `label.py` on the interactive node so you can watch it. For a real labelling run, such as every Item
> 5.02 filing, submit it as a Slurm job of its own. That job needs no GPU, only a few CPU cores: `label.py` sends the
> filings to the server and writes down the answers, and the server does the work on its H200. A job keeps running
> after you log out, and it keeps a long run off the interactive node, which everyone shares.

`label.py` asks Kev the three questions about each filing and saves its answers. It prints its progress every 100
filings and a summary at the end, and `tee` saves the same lines in `$WORK/results/kev-27b-zeroshot.log`. If
`label.py` stops, run the same command again: it skips the filings already answered and sends only the rest.

When all 1,000 are labelled, read the log:

```bash
cat $WORK/results/kev-27b-zeroshot.log
```
{: .yens }

Its last lines are the summary:

```
{
  "filings": 1000,
  "succeeded": 1000,
  "wall_seconds": 192.3,
  "filings_per_second": 5.2,
  "latency_p50": 2.793,
  "latency_p95": 3.958,
  "concurrency": 16
}
```
{: .output }

| Field | What it is |
|---|---|
| `filings` | how many filings `label.py` sent |
| `succeeded` | how many came back with a valid answer. Running the same command again retries the rest. |
| `wall_seconds` | clock time for the whole run, from the first request to the last answer |
| `filings_per_second` | `filings` divided by `wall_seconds`: how fast the server labels, averaged over the run |
| `latency_p50` | the median time for one filing, from sending it to getting the answer: half the filings took less |
| `latency_p95` | 95% of the filings took less than this; only the slowest 5% took longer |
| `concurrency` | how many filings `label.py` kept in flight at once (`--concurrency`) |

`label.py` also saves the summary in `$WORK/results/kev-27b-zeroshot_summary.json`. Later pages print the same
summary.

**Probability or confidence?** The probability of Kev's answer is how likely Kev thinks that answer is: 0.90 for
`status` in this line. Confidence starts from that number and measures it against guessing. With eight options, a
model that knows nothing gives each one a probability of 0.125, so 0.125 tells you nothing; confidence counts it as 0.
A probability of 1 stays 1. In between, confidence is a little lower than the probability: for `why` here, Kev gives
its answer 0.71, and its confidence is 0.67. Both questions have eight options, so sorting Kev's answers by either
number gives the same order.

**When `why` and `future` mean nothing.** `label.py` asks Kev all three questions about every filing, because it
does not know the status until Kev answers. But `why` asks why the CEO is leaving, and `future` asks whether the
change happens later. If the CEO is not leaving, as in this filing, there is no reason and no change, so Kev's answers
to those two questions mean nothing. Here Kev picked "the filing gives no reason for the departure", which is as close
as it can get to "this does not apply". Look at `why` and `future` only for filings that are CEO changes. `score.py`
does the same.

Then score the answers against Jev's:

```bash
$PY scripts/score.py $WORK/results/kev-27b-zeroshot.jsonl
```
{: .yens }

`score.py` prints the scores and saves them in `$WORK/results/kev-27b-zeroshot_scores.json`, next to Kev's answers.
Keep both files, `kev-27b-zeroshot.jsonl` and `kev-27b-zeroshot_scores.json`: they are Kev-27B's results before any
fine-tuning, to compare with a model you fine-tune fully later.
`score.py` takes several answer files at once and prints one row for each, so the two sit side by side.
