# I3. Fine-tune on one Marlowe GPU

**Objective:** run your I2 fine-tune again on one H100 on Marlowe and measure how much faster it trains than on the
Yens. Then train every weight of the model instead of a LoRA adapter, and see what that costs.
{: .fs-6 .fw-300 }

| | |
|---|---|
| Where | Marlowe, 1 H100 |
| Data | `train.jsonl` with Jev's soft labels |
| Model | Part 1: your I2 model, a LoRA adapter on Qwen 4B, with the same settings. Part 2: Kev-4B with every weight trained |

Marlowe is a separate cluster from the Yens, with its own login, its own storage, and nodes of 8 H100 GPUs each.
Nothing you made on the Yens is there, so you set up once more before you train.

## Get onto Marlowe

Log in to Marlowe and make your own copy of this repository in your folder in the class's scratch space. Your
Marlowe home folder holds only 32 GB, so everything you make lives in `/scratch/c001/users/<sunet>`:

```bash
ssh <sunet>@login.marlowe.stanford.edu
```
{: .laptop }

Enter your SUNet password and approve the Duo prompt. Then, on Marlowe:

```bash
mkdir -p /scratch/c001/users/$USER
cd /scratch/c001/users/$USER
git clone https://github.com/gsbdarc/marlowe-hackathon.git
cd marlowe-hackathon
source env/marlowe.sh
```
{: .marlowe }

`source env/marlowe.sh` does on Marlowe what `source scripts/intermediate/yens.sh` did on the Yens. It prints the paths
it set for this terminal:

## Run it: the same fine-tune on one H100

One Slurm job does all of it:

1. Slurm gives the job one H100 on a Marlowe node.
2. The job trains the same model as your I2 job, with the same settings, for about 10 minutes, as I2 did. The H100
   gets through more filings in those 10 minutes than an A40 (1,216, against 512), but each step is still
   8 filings, so the seconds per step compare.
3. It prints the time per step, as your I2 job did.
4. It sends the loss to W&B, which is on the board.

It does not score the model. The training is the same as in I2, so only the speed changes.

{: .important }
> Use the **same settings as your I2 job**, so that the only difference is the GPU. If your I2 command was
> `LR=2e-4 sbatch slurm/yens/intermediate/finetune_kev.slurm`, run `LR=2e-4 sbatch --reservation=GSB_Hackathon slurm/marlowe/intermediate/finetune_kev.slurm`.
> Leave out any `-C GPU_MODEL:...`: every GPU on Marlowe is an H100.

```bash
mkdir -p logs
sbatch --reservation=GSB_Hackathon slurm/marlowe/intermediate/finetune_kev.slurm
```
{: .marlowe }

`sbatch` prints the job's ID. `squeue --me` shows the job: `PD` while it waits for a GPU, `R` once it runs. Follow its
log:

```bash
tail -f logs/i3-finetune-1gpu-<jobid>.out
```
{: .marlowe }

Ctrl-C stops following; the job keeps running. `--reservation=GSB_Hackathon` runs it on the nodes Marlowe has set
aside for the hackathon: 4 nodes of 8 H100s, on Friday from 12:00 to 17:00. The job file asks for the `batch`
partition, the one the class account runs on.

## Compare with the Yens

The last lines of the log are the same table your I2 job printed. This is the one from a I2 run on an A40:

```
run              GPUs steps  s/step peak GPU GB epoch hours epoch GPU-hours
<jobid>             1    64    8.17        22.3        15.0            15.0
```
{: .output }

| Column | What it means |
|---|---|
| `GPUs` | how many GPUs shared the training: 1 here |
| `steps` | optimizer steps the run did; each step trains on 8 filings |
| `s/step` | seconds per step: the median step time, skipping the first 3, which are slower while things warm up |
| `peak GPU GB` | the most memory PyTorch used on the GPU: out of 48 GB on an A40, 80 GB on an H100 |
| `epoch hours` | how long one full pass over `train.jsonl` would take at this speed |
| `epoch GPU-hours` | what that full pass costs: hours × GPUs. It matters from I4, with more than one GPU |

To see your own I2 numbers, look at the end of your I2 log on the Yens:

```bash
tail -3 logs/ceo-finetune-<your I2 jobid>.out
```
{: .yens }

The H100 is a data-center GPU, a generation newer than the A40. Its tensor cores do bf16 arithmetic several times as
fast, and its memory moves data about five times as fast: 3.35 TB per second, against the A40's 696 GB.

<details class="quiz" markdown="1">
<summary><span class="qnum">1</span><span class="qtext">How many times faster is one step on the H100 than on the A40?</span></summary>

Divide the A40's `s/step` by the H100's. Every step of both runs trains on 8 filings, so the difference is the GPU.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">2</span><span class="qtext">How long would a full pass over <code>train.jsonl</code> take on one H100?</span></summary>

`epoch hours`, in the last line of the log. Compare it with the A40's 15 hours from the I2 run above.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">3</span><span class="qtext">How much of the H100's memory did the training use? Is memory what limits you here?</span></summary>

`peak GPU GB`, out of 80. A 4B model with a LoRA adapter uses a fraction of it: what limits you is how fast the GPU
works through the steps, not whether the model fits. I4 adds GPUs to go faster.

</details>

## Part 2: train every weight

Your I2 and I3 jobs trained a **LoRA adapter**: Qwen 4B's 4.2 billion weights stayed frozen, and only 33.8 million
numbers (the adapter and the answer head, under 1% of the model) learned. A **full fine-tune** trains all of them.
Every weight can move, so the model can change more than an adapter lets it, but every weight now needs a gradient
and an optimizer state too.

Count the memory. Training a weight with AdamW, the optimizer Kev uses, takes four numbers for it, not one:

| What | For each weight | Qwen 4B, full fine-tune | Qwen 4B, LoRA (I2) |
|---|---|---|---|
| The weight itself, bf16 | 2 bytes | 8.4 GB | 16.8 GB, frozen: I2 keeps it in fp32 unless `WEIGHTS=bf16` |
| Its gradient, bf16 | 2 bytes | 8.4 GB | adapter only |
| A master copy in fp32, so small updates are not rounded away | 4 bytes | 16.8 GB | adapter only |
| AdamW's two running averages, fp32 | 8 bytes | 33.7 GB | adapter only |
| **Total** | 16 bytes | **67 GB** | **about 17 GB** |

67 GB is most of an H100's 80 GB before the model has looked at a single filing. So on one GPU Kev splits the work:
the weights and gradients stay on the GPU, and the master copies and averages (50 GB) live in the node's memory. After
every step it streams each gradient down to the node, updates the master copy there, and sends the new weight back up.
That traffic is what makes a full fine-tune on one GPU slow.

### Run it

A full fine-tune starts from Kev-4B as full weights: its adapter added into Qwen 4B's matrices once, so that every
weight can train. The first run makes that, in `$WORK/kev-4b-full`, before it trains (under a minute, once):

```bash
sed -i "s/<sunet>/$USER/" slurm/marlowe/intermediate/full_ft_1gpu.slurm
sbatch --reservation=GSB_Hackathon slurm/marlowe/intermediate/full_ft_1gpu.slurm
tail -f logs/i3-full-1gpu-<jobid>.out
```
{: .marlowe }

It trains 100 steps of 16 filings, about 17 minutes, then prints the same table as Part 1. The whole job takes about
20 minutes. Near the top of the log, one line shows the difference from Part 1:

```
device=cuda world=1 trainable params=4207.1M
```
{: .output }

Part 1's log says `trainable params=33.8M`: the adapter and the answer head. Here it is all 4.2 billion. The run also
saves all of them: `$WORK/runs/i3-full/<jobid>` holds 7.9 GB, where a LoRA run saves a 130 MB adapter.

### LoRA or a full fine-tune?

Both runs printed the same table. These are the two runs we did before the event, on one H100 each:

```
run              GPUs steps  s/step peak GPU GB epoch hours epoch GPU-hours
<LoRA jobid>        1   152    2.83        22.2         5.2             5.2
<full jobid>        1   100    9.33        19.5         8.5             8.5
```
{: .output }

| | LoRA (Part 1) | Full fine-tune (Part 2) |
|---|---|---|
| Weights that learn | 33.8 million | 4,207 million, 124 times as many |
| Filings per step | 8 | 16 |
| Seconds per filing | 0.35 | 0.58 |
| One pass over `train.jsonl` | 5.2 hours | 8.5 hours |
| Peak memory on the GPU | 22.2 GB | 19.5 GB, plus about 50 GB of the node's memory |
| What the run saves | a 130 MB adapter | a 7.9 GB model |

Training 124 times as many weights costs only about 1.6 times as long. Most of a step's work is running the filings
through the model, forward and back, and that is the same work either way. The extra in a full fine-tune is the
update of every weight after each step, and the traffic to and from the node's memory that it needs.

The full fine-tune even uses less GPU memory, because its frozen-weight copy is bf16 and the LoRA run's is fp32.
The cost is moved, not saved: the 50 GB of master copies and averages sit in the node's memory instead. That is why
this job asks Slurm for 128 GB of memory, where Part 1 asks for 64 GB.

<details class="quiz" markdown="1">
<summary><span class="qnum">4</span><span class="qtext">How much slower is a full fine-tune than LoRA on the same GPU, per filing?</span></summary>

About 1.6 times. The two runs take different numbers of filings per step (8 and 16), so compare `epoch hours`: the time for one pass
over `train.jsonl`, which already accounts for the filings per step.

</details>

**Use LoRA when** you have one GPU, little data, or many variants to keep: an adapter is 130 MB, a full copy of the
model is 8.4 GB, and a LoRA run fits on a GPU that could never hold a full fine-tune's 67 GB. It also changes the model
less, which helps when you do not want it to forget what it already knew.

**Use a full fine-tune when** you have plenty of data and the task needs the model to change more than an adapter can:
a new domain, a new format, or the last few points of accuracy. It needs the memory, and in practice more than one GPU,
which is what [I4]({{ '/intermediate/i4/' | relative_url }}) is about.
