# I3. Fine-tune on one Marlowe GPU

**Objective:** run your I2 fine-tune again on one H100 on Marlowe and measure how much faster it trains than on the
Yens. Then train every weight of the model instead of a LoRA adapter, and see what that costs.
{: .fs-6 .fw-300 }

| | |
|---|---|
| Where | Marlowe, 1 H100 |
| Data | `train.jsonl` with Jev's soft labels |
| Model | Part 1: your I2 model, a LoRA adapter on Qwen 4B, with the same settings. Part 2: Kev-4B with every weight trained |

Marlowe is a separate cluster from the Yens, with its own login, its own storage, and nodes of 8 H100 GPUs each.
Nothing you made on the Yens is there, so you set up once more before you train.

## Run it: the same fine-tune on one H100

One Slurm job does all of it:

1. Slurm gives the job one H100 on a Marlowe node.
2. The job trains the same model as your I2 job, with the same settings, for about 10 minutes, as I2 did. The H100
   gets through more filings in those 10 minutes than an A40 (1,216, against 512), but each step is still
   8 filings, so the seconds per step compare.
3. It prints the time per step, as your I2 job did.
4. As in I2, it serves the new adapter and scores it on the 2,000 validation and 1,000 test filings, so you can check
   that it learned as much as your I2 run did.
5. It sends the loss and the scores to W&B, which is on the board.

Scoring adds a few minutes after the training (about 7 on an A40 in I2, less on an H100). The training is the same as in I2, so the scores should be close to your I2
run's; what changes is the speed.

{: .important }
> Use the **same settings as your I2 job**, so that the only difference is the GPU. If your I2 command was
> `LR=2e-4 sbatch slurm/yens/intermediate/finetune_kev.slurm`, run `LR=2e-4 sbatch slurm/marlowe/intermediate/finetune_kev.slurm`.
> Leave out any `-C GPU_MODEL:...`: every GPU on Marlowe is an H100.

```bash
mkdir -p logs
sbatch slurm/marlowe/intermediate/finetune_kev.slurm
```
{: .marlowe }

`sbatch` prints the job's ID. `squeue --me` shows the job: `PD` while it waits for a GPU, `R` once it runs. Follow its
log:

```bash
tail -f logs/i3-finetune-1gpu-<jobid>.out
```
{: .marlowe }

Ctrl-C stops following; the job keeps running. The job runs on `batch`, the partition the class account uses, and
waits there behind everyone else's jobs. On Friday from 12:00 to 17:00, Marlowe sets aside 4 nodes of 8 H100s for
the hackathon, the `GSB_Hackathon` reservation. While it is open, `source env/marlowe.sh` sends your jobs there by
itself and says so (`jobs go to: batch, in the GSB_Hackathon reservation`). If you sourced it before 12:00, source it
again.

## Compare with the Yens

The last lines of the log are the same table your I2 job printed. This is the one from a I2 run on an A40:

```
run              GPUs steps  s/step peak GPU GB epoch hours epoch GPU-hours
<jobid>             1    64    8.17        22.3        15.0            15.0
```
{: .output }

| Column | What it means |
|---|---|
| `GPUs` | how many GPUs shared the training: 1 here |
| `steps` | optimizer steps the run did; each step trains on 8 filings |
| `s/step` | seconds per step: the median step time, skipping the first 3, which are slower while things warm up |
| `peak GPU GB` | the most memory PyTorch used on the GPU: out of 48 GB on an A40, 80 GB on an H100 |
| `epoch hours` | how long one full pass over `train.jsonl` would take at this speed |
| `epoch GPU-hours` | what that full pass costs: hours × GPUs. It matters from I4, with more than one GPU |

To see your own I2 numbers, look at the end of your I2 log on the Yens:

```bash
tail -3 logs/ceo-finetune-<your I2 jobid>.out
```
{: .yens }

The H100 is a data-center GPU, a generation newer than the A40. Its tensor cores do bf16 arithmetic several times as
fast, and its memory moves data about five times as fast: 3.35 TB per second, against the A40's 696 GB.

## Part 2: train every weight

Your I2 and I3 jobs trained a **LoRA adapter**: Qwen 4B's 4.2 billion weights stayed frozen, and only 33.8 million
numbers (the adapter and the answer head, under 1% of the model) learned. A **full fine-tune** trains all of them.
Every weight can move, so the model can change more than an adapter lets it, but every weight now needs a gradient
and an optimizer state too.

Count the memory. Training a weight with AdamW, the optimizer Kev uses, takes four numbers for it, not one:

| What | For each weight | Qwen 4B, full fine-tune | Qwen 4B, LoRA (I2) |
|---|---|---|---|
| The weight itself, bf16 | 2 bytes | 8.4 GB | 16.8 GB, frozen: I2 keeps it in fp32 unless `WEIGHTS=bf16` |
| Its gradient, bf16 | 2 bytes | 8.4 GB | adapter only |
| A master copy in fp32, so small updates are not rounded away | 4 bytes | 16.8 GB | adapter only |
| AdamW's two running averages, fp32 | 8 bytes | 33.7 GB | adapter only |
| **Total** | 16 bytes | **67 GB** | **about 17 GB** |

67 GB is most of an H100's 80 GB before the model has looked at a single filing. So on one GPU Kev splits the work:
the weights and gradients stay on the GPU, and the master copies and averages (50 GB) live in the node's memory. After
every step it streams each gradient down to the node, updates the master copy there, and sends the new weight back up.
That traffic is what makes a full fine-tune on one GPU slow.

### Run it

A full fine-tune starts from Kev-4B as full weights: its adapter added into Qwen 4B's matrices once, so that every
weight can train. The first run makes that, in `$WORK/kev-4b-full`, before it trains (under a minute, once).

First, put your SUNet ID in this job file too, so Slurm emails you when the job starts, ends or fails:

<details markdown="1" id="what-each-full-setting-does">
<summary>What each setting does, and what it trades</summary>

#### Learning rate

A full fine-tune moves all 4.2 billion weights, not a small adapter beside them, so the same learning rate changes
the model far more than in I2. Too large, and the updates can overwrite what Kev-4B already knew, which shows as a
loss that jumps or rises; too small, and 100 steps barely move it. 2e-5 is the default; 5e-6 is the cautious choice
people often use for full fine-tunes, and 1e-4 shows what too large looks like.

#### Filings per step

How many filings the job adds up before one update. With the same filings to train on, this sets how many updates
you get: 200 at 8 per step, 100 at 16, 50 at 32. Fewer per step give more, noisier updates. A bigger batch needs no
more GPU memory, because the job still works on one filing at a time. Unlike I2, every update here is expensive: each
one streams 4.2 billion gradients to the node's memory and the new weights back, so fewer, larger steps spend less
of the job on updates.

#### Filings to train on

How much the model sees, and so how long the job takes: about 0.58 seconds a filing on one H100, plus a few minutes to
load and save. 800 filings is about 8 minutes of training, 1,600 about 17, 3,200 about 33. All are a small part of
`train.jsonl`'s 52,757 filings.

</details>

### LoRA or a full fine-tune?

{: .important }
> **How much data you have, and how much of it you can train on, decides this more than anything else.** A full
> fine-tune sets 124 times as many numbers as LoRA. To set them well it needs far more training data, and the hours to
> work through it. With a few thousand examples, LoRA is usually the better choice. A full fine-tune earns its cost
> when you have tens of thousands of examples or more, and the GPUs to train on all of them.

Both runs printed the same table. These are the two runs we did before the event, on one H100 each:

```
run              GPUs steps  s/step peak GPU GB epoch hours epoch GPU-hours
<LoRA jobid>        1   152    2.83        22.2         5.2             5.2
<full jobid>        1   100    9.33        19.5         8.5             8.5
```
{: .output }

| | LoRA (Part 1) | Full fine-tune (Part 2) |
|---|---|---|
| Weights that learn | 33.8 million | 4,207 million, 124 times as many |
| Filings per step | 8 | 16 |
| Seconds per filing | 0.35 | 0.58 |
| One pass over `train.jsonl` | 5.2 hours | 8.5 hours |
| Filings trained on in an hour | about 10,300 | about 6,200 |
| Peak memory on the GPU | 22.2 GB | 19.5 GB, plus about 50 GB of the node's memory |
| What the run saves | a 130 MB adapter | a 7.9 GB model |

Training 124 times as many weights costs only about 1.6 times as long. Most of a step's work is running the filings
through the model, forward and back, and that is the same work either way. The extra in a full fine-tune is the
update of every weight after each step, and the traffic to and from the node's memory that it needs.

The full fine-tune even uses less GPU memory, because its frozen-weight copy is bf16 and the LoRA run's is fp32.
The cost is moved, not saved: the 50 GB of master copies and averages sit in the node's memory instead. That is why
this job asks Slurm for 128 GB of memory, where Part 1 asks for 64 GB.

#### Data decides

Two things make the amount of data matter so much.

- **How much data you have.** Every trained number is set by the examples it learns from. LoRA has 33.8 million to
  set, and a full fine-tune 4,207 million. With a small training set, a full fine-tune has far more freedom than the
  data can pin down: it can memorize the training filings (overfitting), or drift away from what Kev-4B already
  knew. LoRA changes the model less, so a small set is enough for it. With a large set, a full fine-tune has the data
  to use its extra freedom, and that is where it pulls ahead.
- **How much of it you can get through.** On one H100 a full fine-tune takes 0.58 seconds a filing, and LoRA 0.35. In
  the same slot, LoRA trains on about 1.6 times as many filings:

This run's 1,600 filings are 3% of `train.jsonl`. That is enough to measure the speed and the memory, but not to
show what a full fine-tune could learn from all 52,757. Training on all of them in under an hour instead of 8.5 is
what [I4]({{ '/intermediate/i4/' | relative_url }}) does, with 8 GPUs.

| Your training data | Usually choose |
|---|---|
| A few hundred to a few thousand examples | LoRA |
| Tens of thousands or more, with the GPUs and hours to train on all of them | a full fine-tune can pay off |
| Many tasks or variants of one model to keep | LoRA: one 130 MB adapter each, instead of a 7.9 GB model |

**Use LoRA when** you have little data, or little time to train on it. It also suits one GPU, or many variants to
keep: an adapter is 130 MB, a full copy of the model is 8.4 GB, and a LoRA run fits on a GPU that could never hold a
full fine-tune's 67 GB. It changes the model less, which helps when you do not want it to forget what it already knew.

**Use a full fine-tune when** you have plenty of data, and the hours and GPUs to train on all of it, and the task needs
the model to change more than an adapter can: a new domain, a new format, or the last few points of accuracy. It needs
the memory, and in practice more than one GPU, which is what [I4]({{ '/intermediate/i4/' | relative_url }}) is about.

<details class="quiz" markdown="1">
<summary><span class="qnum">4</span><span class="qtext">Before you change every weight of a model, what matters most?</span></summary>

1. **Data.** Do you have enough of it? A full fine-tune sets 4,207 million numbers, 124 times as many as LoRA. With a
   few thousand examples it can memorize them or drift from what the model knew. It needs tens of thousands or more.
2. **Time to train on it.** A full fine-tune takes about 1.6 times as long per filing on the same GPU: 0.58 seconds
   against 0.35, and 8.5 hours against 5.2 for one pass over `train.jsonl`. Compare `epoch hours`, not seconds per
   step, because the two runs take different numbers of filings per step (16 and 8).
3. **Memory.** Every weight needs 16 bytes to train: 67 GB for Qwen 4B before it reads a single filing. On one H100,
   Kev moves 50 GB of it to the node's memory, which is why this job asks for 128 GB. A bigger model needs several GPUs.
4. **What the model might lose.** Every weight can move, so a learning rate that is too large can overwrite what the
   model already knew. Use a cautious one, and check the validation scores against Kev-4B as released.
5. **What you keep.** Each run saves a 7.9 GB model, where a LoRA run saves a 130 MB adapter.

If you can't say yes to the first two, start with LoRA.

</details>
