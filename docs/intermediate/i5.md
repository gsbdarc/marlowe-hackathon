# I5. Inference at scale

**Objective:** label filings with Kev on 2 and then 4 H100s, see that labeling scales with the GPUs, and work out
what labeling all 296,477 filings would take on 8, 16 or more, and what it costs compared with Jev.
{: .fs-6 .fw-300 }

| | |
|---|---|
| Where | Marlowe, 2 H100s, then 4 |
| Data | the first 32,000 of the 296,477 Item 5.02 filings since 2004 with text; no labels needed |
| Model | Kev-4B as released, or your own fine-tune from I3 or I4 |

You need I3's setup done: your clone on Marlowe, Kev checked, and `source env/marlowe.sh`.

---

## Two ways to use several GPUs

In I4, the GPUs trained **one** model together. FSDP2 split every weight among them and gathered each layer as it
ran; DDP gave each GPU a whole copy and added up the gradients after every step. Either way, the GPUs talked to each
other at every step, because they were all changing the same model.

Labeling is different. Serving Kev-4B needs only its bf16 weights, about 9 GB, plus room for the filings in flight:
in our runs each H100 peaked at 26 GB of its 80. One GPU holds the whole model with room to spare, so there is nothing
to split. Instead, give each GPU **its own copy** of the model and **its own share of the filings**:

- One Kev server starts per GPU. `CUDA_VISIBLE_DEVICES=3` shows server 3 only GPU 3.
- The filings are dealt into one **shard** per GPU: on 4 GPUs, filing 0 to shard 0, filing 1 to shard 1, ..., filing 4
  back to shard 0.
- One copy of `label.py` per shard sends its filings to its own server.

The GPUs never talk to each other. Each one does exactly what a single GPU does in I1, on its share of the filings.
This is **data parallelism** with no communication at all, sometimes called *embarrassingly parallel*: the easiest
kind of scaling there is.

| | I4: train one model | I5: label filings |
|---|---|---|
| What is split | the model's weights (FSDP2) | the filings (shards) |
| Copies of the model | 1 (FSDP2: in pieces; DDP: copied, kept in step) | one per GPU, each on its own |
| GPUs talk to each other | every step, over NVLink | never |
| Speedup on 8 GPUs | 9.2 times for our full fine-tune; usually less than 8 | almost exactly 8 |
| Needs | the model too big or too slow for one GPU | the model fits on one GPU |

<details markdown="1">
<summary>What if the model did not fit on one GPU?</summary>

Then each copy has to span several GPUs, and those GPUs do talk. That is the Advanced track's
[A4]({{ '/advanced/a4/' | relative_url }}): Qwen 235B has 237 GB of weights, so vLLM splits each layer across all 8
H100s (*tensor parallelism*) and the whole node serves one copy. To label faster still, you would start more copies,
one per node, and shard the filings across nodes: the same idea as here, one level up.

</details>

{: .note }
> **Use the reservation.** From 12:00 to 17:00, `source env/marlowe.sh` sends your jobs to the hackathon's own nodes,
> the `GSB_Hackathon` reservation, and says so: `jobs go to: batch, in the GSB_Hackathon reservation`. If your shell
> was opened before 12:00, or does not say that, run `source env/marlowe.sh` again before you submit. A job submitted
> without it waits in the queue behind everyone else's.

Two jobs, on the **same first 32,000 filings**: one on 2 H100s, 16,000 filings each, and one on 4, 8,000 each. Submit
both; they do not need to run at the same time:

```bash
sed -i "s/<sunet>/$USER/" slurm/marlowe/intermediate/label_2gpu.slurm slurm/marlowe/intermediate/label_4gpu.slurm
sbatch slurm/marlowe/intermediate/label_2gpu.slurm      # 32,000 filings on 2 H100s
sbatch slurm/marlowe/intermediate/label_4gpu.slurm      # the same 32,000 on 4 H100s
tail -f logs/i5-label-4gpu-<jobid>.out
```
{: .marlowe }

Each job's log follows GPU 0's shard; the others are in `$WORK/results/i5/<jobid>/shard-<n>.log`. From our 4-GPU job:

```

```
{: .output }

The rate climbs over the first thousand or so filings while the server warms up, then holds. The first time you run
Kev on Marlowe, the servers also compile their GPU kernels, which is most of a load of 1 to 3 minutes; later jobs load
faster.

| Setting | Default | Change it with |
|---|---|---|
| Model | Kev-4B as released | `RUN=$WORK/runs/i4/<jobid>` (an I4 full fine-tune), `RUN=$WORK/runs/lora-ddp/<jobid>` (an I4 LoRA) or `RUN=$WORK/runs/i3/<jobid>` (I3's LoRA) |
| Filings | the first 32,000 | `FILINGS=0` for all 296,477: about 1 hour 4 minutes on 2 GPUs, so it needs a longer `--time` |
| Filings in flight, per GPU | 64 | `CONCURRENCY=16`; 64 is the most a Kev server batches at once |

Every answer is saved as it arrives, one line per filing, in `$WORK/results/i5/<jobid>/shard-<n>.jsonl`.

## Compare 2 GPUs with 4

At the end, each job prints its summary. Print both side by side:

```bash
$PY scripts/intermediate/shards.py $WORK/results/i5/<2-GPU jobid> $WORK/results/i5/<4-GPU jobid>
```
{: .marlowe }

```

Until then, the numbers below are expected ones, from 38.6 filings/s per GPU in Natalya's 8-GPU run.
```

{: .output }

`filings/s` is the job's rate over all its GPUs. `all hours` and `GPU-hours` are what labeling all 296,477 filings
would take at that rate, `GPUs $` prices those GPU-hours at $3 an hour, and `Jev $` is what the same filings cost from
Jev. These are our two test jobs, the day before the event.

Each job also sends its totals to W&B as one run, in the room's project
[Marlowe-Hackathon/Intermediate Exercise 5](https://forge.coreweave.com/wandb/Marlowe-Hackathon/Intermediate%20Exercise%205):
`filings_per_second` across all its GPUs, `filings_per_second_per_gpu`, the load time, and the hours and dollars to
label every filing. The run's name says how many GPUs it used (`<sunet>-h100x4-kev-4b-<jobid>`), so the board shows
everyone's 2- and 4-GPU jobs side by side.

<summary><span class="qnum">1</span><span class="qtext">How many times faster is 4 GPUs than 2? Why not more?</span></summary>

154.4 ÷ 77.2: about 2.00 times, against a most of 2. Per GPU, the two jobs ran at 38.6 and

The little that is lost is the job waiting for its slowest shard, and each shard's first minute, while its server
warms up. Compare I4, where the GPUs had to talk at every step.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">2</span><span class="qtext">Which costs more, 2 GPUs or 4?</span></summary>

About the same: 2.13 against 2.13 GPU-hours for every filing. 4 GPUs for
half the time cost what 2 cost for all of it. When scaling is close to linear, more GPUs buy you time for free.

What is not free is loading: each GPU spends its first minute or so loading the model, labeling nothing. The more GPUs,

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">3</span><span class="qtext">How busy were the GPUs, and how much memory did they use?</span></summary>

Look at `logs/gpu-<jobid>.csv`. In our runs each GPU was about 81% busy while labeling, and used 23 to 26 GB of its
80 GB. There is room for more filings in flight, but a Kev server batches at most 64 at once; to fill an H100 you could
start two servers per GPU, each with its own shard.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">4</span><span class="qtext">How often did Kev-4B agree with Jev over all 296,477 filings?</span></summary>

We labeled every filing once before the event (see [Scale it up](#scale-it-up)) and matched each answer with Jev's in
`$DATA/item502_v1.parquet`. Kev-4B as released gave Jev's status on 88% of filings and agreed on whether the CEO is
leaving on 91%, about the same on the training, validation and test years. Jev itself is not ground truth (see
[I1]({{ '/intermediate/i1/' | relative_url }})): this is how closely the student copies the teacher, now over every
filing instead of the 1,000 test filings.

</details>

## Scale it up

Your two jobs give one GPU's rate: about 39 filings per second. Nothing passes between the GPUs, so N of them
label N times as fast, and labeling every filing takes 296,477 ÷ (39 × N) seconds. Add a 20-second warm load on
every GPU:

| GPUs | Labeling all 296,477 filings | GPU-hours | At $3 per GPU-hour | From |
|---|---|---|---|---|
| 1 | 2 hours 8 minutes | 2.14 | $6.42 | worked out |
| 2 | 1 hour 4 minutes | 2.14 | $6.43 | your jobs' rate |
| 4 | 32 minutes | 2.16 | $6.47 | your jobs' rate |
| 6 | 21 minutes | 2.17 | $6.50 | worked out |
| 8 | 16 minutes | 2.18 | $6.53 | worked out; Natalya's job took 16.2 minutes |
| 16 | 8 minutes | 2.22 | $6.67 | worked out |
| 32 | 4 minutes | 2.31 | $6.93 | worked out |
| 128 | 60 seconds | 2.84 | $8.53 | worked out |

The time keeps halving, but the load does not shrink: every GPU spends its first 20 seconds loading the model whatever
the job's size. Once labeling takes a minute, the load is a quarter of the cost, and a cold first load of 3 minutes
would be most of it. Waiting for a whole node, or 16 of them, also takes longer than waiting for one GPU. Scale out
when you are waiting on the answer; stay small when you are not.

**We checked the 8-GPU row.** Natalya labeled every filing on one node before the event (job 555394, on n14,
`label_8gpu.slurm`): 305.6 filings per second, 38.2 to 39.2 per GPU, all 296,477 in 16.2 minutes, and 19.2 with the
cold load of 176 s.

The fastest and slowest shards finished 24 seconds apart. Dealing the filings out one at a time, rather than in
8 blocks of consecutive filings, is what keeps them that close: every shard gets the same mix of years, and of
short and long filings, so no GPU is left with all the long ones.

</details>

<details markdown="1">
<summary>How you would run it on more than one node</summary>

One node has 8 GPUs. Past that, each node is a separate Slurm job in a **job array**, and each labels its own 8 of the
shards:

```bash
SHARDS=16 sbatch --array=0-1 slurm/marlowe/intermediate/label_8gpu.slurm      # 2 nodes, 16 GPUs: shards 0-7 and 8-15
SHARDS=32 sbatch --array=0-3 slurm/marlowe/intermediate/label_8gpu.slurm      # 4 nodes, 32 GPUs
```

Every task writes into the same `$WORK/results/i5/<array jobid>/`, and `shards.py` adds them up once all are done. We
tried it small, two tasks of one GPU each: they ran on n14 and n21, labeled 2,000 filings each, and not one filing
twice. The nodes do not need to run at the same time: if only one is free, the tasks take turns, and the answers are
the same. (Do not run these today: the room shares four nodes.)

</details>

The same holds for more data. Every Form 8-K since 2004, not just those with Item 5.02, is 1.77 million filings
(`$DATA/index_8k_items_2004_2026.parquet`), 6 times as many. If they were as long as these, that would be an hour and
a half on one node, or 12 minutes on 8 nodes.

<details markdown="1">
<summary>Why save as you go</summary>

A long job on a shared cluster can be stopped halfway: a node fails, or, on a partition like Marlowe's `preempt`, a
job with a higher priority takes the GPUs back. Slurm then puts the job back in the queue with the same job ID.

`label.py` saves each answer as it arrives and, on a rerun, skips every filing already answered. We ran a 1-GPU job on
`preempt` before the event. It was taken back with 23,544 of its 37,060 answers saved
(`JOB 555386 ON n13 CANCELLED ... DUE TO PREEMPTION`), and its second start said

```
37,060 filings, 23,544 already answered, 13,516 to send at concurrency 64
```

It was preempted once more, just as it sent its last filing; its third start, on another node, found all 37,060
answered and sent nothing. Three starts on three nodes, and not one filing labeled twice or lost.

For long jobs, this is the habit to copy: save as you go, and make a rerun pick up where the last one stopped. You can
do the same by hand: resubmit with the same output folder and only the missing filings are sent.

</details>

## How much money you saved

Labeling all 296,477 filings, 342 million tokens of text:

| | Cost | Time |
|---|---|---|
| Jev, at $42 per billion input tokens | $14.38 | about 20 minutes, on TypeSafe's servers |
| Kev-4B on 8 H100s, at $3 per GPU-hour (a typical 2026 cloud price) | $6.47, or $7.75 with loading | 16 minutes (19 with loading) |
| Kev-4B on 8 H100s, at $11 to $12 per GPU-hour (the big clouds' list price) | $24 to $31 | the same |
| Kev-4B on Marlowe | no bill: the project's allocation covers it | the same, plus the wait in the queue |

At a typical cloud price, Kev did Jev's job for about half the cost. At the big clouds' list price it costs more than
Jev. Both are a few dollars: at this size, money is not why you train your own model.

The savings come from doing it **again**:

- **Every new model is another full run.** Each fine-tune you try in I2 and I3 has to label the filings to be
  compared. From Jev, every run would be another $14; from Kev on Marlowe, it costs queue time.
- **New questions.** Asking Jev something new means paying for all 342 million tokens again. A Kev fine-tuned on
  those answers once labels any number of filings, or new filings as they come, for GPU time.
- **A chat model costs far more.** The same 342 million tokens sent to a general chat model, at $1 to $3 per million
  input tokens, would be $340 to $1,030, before output tokens, and its answers would still need parsing (I1).
- **The filings never leave Marlowe.** For data you cannot send to an outside service, a model you run yourself is
  the only option.

What Kev cannot do is replace Jev as the teacher. Kev learned from Jev's labels; it agrees with them on 88% of
filings. Jev made the labels once, for $14; Kev copies them as often as you like.
