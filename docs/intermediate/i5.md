# I5. Inference at scale

**Objective:** label every one of the 296,477 filings with Kev on the 8 H100s of one Marlowe node, then work out how
it would scale to more nodes and what it costs compared with Jev.
{: .fs-6 .fw-300 }

| | |
|---|---|
| Where | Marlowe, 1 H100, then 8 H100s (one node) |
| Data | every Item 5.02 filing since 2004 with text: 296,477, no labels needed |
| Model | Kev-4B as released, or your own fine-tune from I3 |

You need I3's setup done: your clone on Marlowe, Kev checked, and `source env/marlowe.sh`.

---

## Two ways to use 8 GPUs

In I4, 8 GPUs trained **one** model together: FSDP2 split every weight 8 ways, and the GPUs talked to each other at
every layer. That was worth it because a full fine-tune needs 67 GB and grows with the model.

Labeling is different. Serving Kev-4B needs only its bf16 weights, about 9 GB, plus room for the filings in flight:
in our runs each H100 peaked at 26 GB of its 80. One GPU holds the whole model with room to spare, so there is nothing
to split. Instead, give each GPU **its own copy** of the model and **its own share of the filings**:

- 8 Kev servers start, one per GPU. `CUDA_VISIBLE_DEVICES=3` shows server 3 only GPU 3.
- The filings are dealt into 8 **shards**: filing 0 to shard 0, filing 1 to shard 1, ..., filing 8 back to shard 0.
- 8 copies of `label.py`, one per shard, each send their filings to their own server.

The 8 GPUs never talk to each other. Each one does exactly what a single GPU does in I1, on an eighth of the filings.
This is **data parallelism** with no communication at all, sometimes called *embarrassingly parallel*: the easiest
kind of scaling there is.

| | I4: train one model | I5: label filings |
|---|---|---|
| What is split | the model's weights (FSDP2) | the filings (shards) |
| Copies of the model | 1, in 8 pieces | 8, each whole |
| GPUs talk to each other | at every layer, over NVLink | never |
| Speedup on 8 GPUs | 9.2 times, here; usually less than 8 | almost exactly 8 |
| Needs | the model too big or too slow for one GPU | the model fits on one GPU |

<details markdown="1">
<summary>What if the model did not fit on one GPU?</summary>

Then each copy has to span several GPUs, and those GPUs do talk. That is the Advanced track's
[A4]({{ '/advanced/a4/' | relative_url }}): Qwen 235B has 237 GB of weights, so vLLM splits each layer across all 8
H100s (*tensor parallelism*) and the whole node serves one copy. To label faster still, you would start more copies,
one per node, and shard the filings across nodes: the same idea as here, one level up.

</details>

## Run it

Two jobs. First one GPU's share alone, to see what one H100 does; then all 8 shards on a whole node:

```bash
sed -i "s/<sunet>/$USER/" slurm/marlowe/intermediate/label_1gpu.slurm slurm/marlowe/intermediate/label_8gpu.slurm
sbatch slurm/marlowe/intermediate/label_1gpu.slurm      # shard 0 of 8: 37,060 filings on one H100
sbatch slurm/marlowe/intermediate/label_8gpu.slurm      # all 8 shards: 296,477 filings on 8 H100s
tail -f logs/i5-label-8gpu-<jobid>.out
```
{: .marlowe }

The 8-GPU job's log follows GPU 0's shard; the others are in `$WORK/results/i5/<jobid>/shard-<n>.log`:

```
8 Kev servers ready in 176 s on n14: jaredpalmer/kev-4b@v1.0
37,060 filings, 0 already answered, 37,060 to send at concurrency 64
  100/37,060  11.2 filings/s  failed 0
  ...
  37,000/37,060  38.5 filings/s  failed 0
```
{: .output }

The rate climbs over the first few thousand filings while the server warms up, then holds. The first time you run
Kev on Marlowe, the servers also compile their GPU kernels, which is most of the 176 s; later jobs load in about 20 s.

| Setting | Default | Change it with |
|---|---|---|
| Model | Kev-4B as released | `RUN=$WORK/runs/i3/<jobid>`, your LoRA from I3 |
| Filings | all 296,477 | `FILINGS=16000`: only the first 16,000, in filing order |
| Filings in flight, per GPU | 64 | `CONCURRENCY=16`; 64 is the most a Kev server batches at once |
| Shards | one per GPU | `SHARDS=16`, with a job array: see [Scale it up](#scale-it-up) |

Every answer is saved as it arrives, one line per filing, in `$WORK/results/i5/<jobid>/shard-<n>.jsonl`. All of them
together are 450 MB.

## Compare 1 GPU with 8

At the end, each job prints its summary. Print both side by side:

```bash
$PY scripts/intermediate/shards.py $WORK/results/i5/<1-GPU jobid> $WORK/results/i5/<8-GPU jobid>
```
{: .marlowe }

```
job        GPUs  filings failed filings/s load s all hours GPU-hours  GPUs $  Jev $
<1-GPU>       1   37,060      0      39.4     20      2.09      2.09    6.27  14.38
<8-GPU>       8  296,477      0     305.6    176      0.27      2.16    6.47  14.38
```
{: .output }

`all hours` and `GPU-hours` are what labeling all 296,477 filings takes at the job's rate; for the 1-GPU job, that
is 8 times its one shard. `GPUs $` prices those GPU-hours at $3 an hour, and `Jev $` is what the same filings cost from
Jev. These are the runs we did before the event: the 8-GPU job labeled every filing in 16.2 minutes, and took 19
minutes in all with loading the servers. The 1-GPU job's rate is its steady rate, which held at 39.4 filings per
second once the server had warmed up.

<details class="quiz" markdown="1">
<summary><span class="qnum">1</span><span class="qtext">How many times faster is the node than one GPU? Why not more?</span></summary>

305.6 ÷ 39.4: about 7.8 times, against a most of 8. Each GPU on the node did 38.2 to 39.2 filings per second, within
3% of the 39.4 of a GPU on its own, because nothing passes between them.

The little that is lost is the job waiting for its slowest shard: the 8 shards took between 946 and 970 seconds,
and the job ends with the last. Compare I4, where 8 GPUs had to gather weights and add up
gradients at every layer.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">2</span><span class="qtext">Which costs more, 1 GPU or 8?</span></summary>

About the same: 2.09 against 2.16 GPU-hours for every filing. 8 GPUs for a quarter of an hour cost what 1 GPU costs
for 2 hours. When scaling is close to linear, more GPUs buy you time for free.

What is not free is loading: each GPU spends its first 20 s to 3 minutes loading the model, labeling nothing. On one
GPU that is a sliver of 2 hours; on 8 GPUs it is 3 of the job's 19 minutes. Counting the whole job, the node used
8 × 19.4 minutes, 2.6 GPU-hours.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">3</span><span class="qtext">How busy were the GPUs, and how much memory did they use?</span></summary>

Look at `logs/gpu-<jobid>.csv`. In our run each GPU was about 81% busy while labeling, and used 23 to 26 GB of its
80 GB. There is room for more filings in flight, but a Kev server batches at most 64 at once; to fill an H100 you could
start two servers per GPU, each with its own shard.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">4</span><span class="qtext">How often did Kev-4B agree with Jev over all 296,477 filings?</span></summary>

We matched each filing's answer with Jev's in `$DATA/item502_v1.parquet`. Kev-4B as released gave Jev's status on
88% of filings and agreed on whether the CEO is leaving on 91%, about the same on the training, validation and test
years. Jev itself is not ground truth (see [I1]({{ '/intermediate/i1/' | relative_url }})): this is how closely the
student copies the teacher, now over every filing instead of the 1,000 test filings.

</details>

## The 8-GPU run, in detail

The 8-GPU numbers on this page come from Natalya's run of `label_8gpu.slurm`, before the event, on one node of the
hackathon's prep reservation:

| Labeling | 970 s for the slowest shard: 16.2 minutes |
| Whole job | 1,152 s: 19.2 minutes |
| Filings in flight | 64 per GPU |

Each GPU's shard, from `$WORK/results/i5/555394/shard-<n>_summary.json`:

|---|---|---|---|
| 0 | 37,060 | 961.9 | 38.5 |

## Why distribute it

Set the 8-GPU run beside the same work on one H100, at the 39.4 filings per second one GPU holds:

| | 1 H100 | 8 H100s, one shard each |
|---|---|---|
| Labeling every filing | 2 hours 5 minutes | 16.2 minutes (19.2 with loading) |
| GPU-hours, labeling | 2.09 | 2.16 |
| Each GPU's speed | 39.4 filings/s | 38.2 to 39.2 filings/s |
| What the GPUs send each other | nothing | nothing |
| Code changed | none | none: the same server and `label.py`, 8 times |
| Getting the GPUs | quick: any free GPU | slower: a whole free node |
| Loading the model | once | on every GPU, at the same time |

**The benefit is time, almost for free.** The node gave the answer 7.8 times sooner for 3% more GPU-hours. That is
rare: in I4, 8 GPUs had to gather weights and add up gradients at every layer, and in most training the GPU-hours
grow with the GPUs. Here each GPU works alone, so 8 of them do 8 times the work in the same time.

**It changes what you can try.** At 2 hours a pass, labeling every filing with a new fine-tune is an overnight job;
at 16 minutes, you can label everything with each I3 run and compare them on all 296,477 filings, not only the 1,000
test filings.

**It scales past one node the same way.** Nothing in a shard depends on another, so 16 or 128 GPUs work like 8:
see [Scale it up](#scale-it-up). And because each shard saves its answers as it goes, a stopped shard loses only its
own unfinished filings, not the others'.

**What it costs is the overhead and the wait.** Every GPU loads the model before it labels anything: 176 s cold here,
about 20 s warm: a sixth of this job, but a sliver of a 2-hour one. A whole node can take longer to get than one GPU;
Natalya's ran in the reservation, where the node was waiting. If you are not waiting on the answer, one GPU does the
same work for the same GPU-hours.

## When the job is stopped halfway

The `preempt` partition lets anyone's job run on idle GPUs, but a job with a higher priority can take them back at
any moment. Ours was: the 1-GPU job had saved 23,544 of its 37,060 answers when its log ended with

```
error: *** JOB 555386 ON n13 CANCELLED AT 2026-11-04T11:49:40 DUE TO PREEMPTION ***
```
{: .output }

Slurm put the job back in the queue with the same job ID. When it starts again it carries on: `label.py` saves each
answer as it arrives and, on a rerun, skips every filing already answered:

```
37,060 filings, 23,544 already answered, 13,516 to send at concurrency 64
```
{: .output }

Ours was preempted once more, on n10, just as it sent its last filing, and its third start, on n21, found all 37,060
answered and sent nothing. Three starts on three nodes, and not one filing labeled twice or lost.

For long jobs on shared clusters, this is the habit to copy: save as you go, and make a rerun pick up where the last
one stopped. You can do the same by hand: resubmit with the same output folder and only the missing filings are sent.

## Scale it up

One node took 16 minutes. For more data, or less time, add nodes. Each node is a separate Slurm job in a **job
array**, and each labels its own 8 of the shards:

```bash
SHARDS=16 sbatch --array=0-1 slurm/marlowe/intermediate/label_8gpu.slurm      # 2 nodes, 16 GPUs: shards 0-7 and 8-15
SHARDS=32 sbatch --array=0-3 slurm/marlowe/intermediate/label_8gpu.slurm      # 4 nodes, 32 GPUs
```
{: .marlowe }

Every task writes into the same `$WORK/results/i5/<array jobid>/`, and `shards.py` adds them up once all are done.
We tried it small, two tasks of one GPU each (`SHARDS=2 FILINGS=4000 sbatch --array=0-1 slurm/marlowe/intermediate/label_1gpu.slurm`):
they ran on n14 and n21, labeled 2,000 filings each, and not one filing twice. The
nodes do not need to run at the same time: if only one is free, the tasks take turns, and the answers are the same.

What more nodes would give, at 38.5 filings per second per GPU and a 20-second warm load:

| | GPUs | Labeling every filing | GPU-hours | At $3 per GPU-hour |
|---|---|---|---|---|
| 1 GPU | 1 | 2 hours 9 minutes | 2.14 | $6.43 |
| 1 node | 8 | 16 minutes | 2.18 | $6.55 |
| 2 nodes | 16 | 8 minutes | 2.23 | $6.68 |
| 4 nodes | 32 | 4 minutes | 2.32 | $6.95 |
| 16 nodes | 128 | 1 minute 20 seconds | 2.85 | $8.55 |

The time keeps halving, but the load does not shrink: every GPU spends its first 20 seconds loading the model whatever
the job's size. Once labeling takes a minute, the load is a quarter of the cost, and the cold first load of
3 minutes would be most of it. Waiting for a whole node, or 16 of
them, also takes longer than waiting for one GPU. Scale out when you are waiting on the answer; stay small when you
are not.

The same holds for more data. Every Form 8-K since 2004, not just those with Item 5.02, is 1.77 million filings
(`$DATA/index_8k_items_2004_2026.parquet`), 6 times as many. If they were as long as these, that would be an hour and
a half on one node, or 12 minutes on 8 nodes.

## How much money you saved

Labeling all 296,477 filings, 342 million tokens of text:

| | Cost | Time |
|---|---|---|
| Jev, at $42 per billion input tokens | $14.38 | about 20 minutes, on TypeSafe's servers |
| Kev-4B on 8 H100s, at $3 per GPU-hour (a typical 2026 cloud price) | $6.47, or $7.75 with loading | 16 minutes (19 with loading) |
| Kev-4B on 8 H100s, at $11 to $12 per GPU-hour (the big clouds' list price) | $24 to $31 | the same |
| Kev-4B on Marlowe | no bill: the project's allocation covers it | the same, plus the wait in the queue |

At a typical cloud price, Kev did Jev's job for about half the cost. At the big clouds' list price it costs more than
Jev. Both are a few dollars: at this size, money is not why you train your own model.

The savings come from doing it **again**:

- **Every new model is another full run.** Each fine-tune you try in I2 and I3 has to label the filings to be
  compared. From Jev, every run would be another $14; from Kev on Marlowe, it costs queue time.
- **New questions.** Asking Jev something new means paying for all 342 million tokens again. A Kev fine-tuned on
  those answers once labels any number of filings, or new filings as they come, for GPU time.
- **A chat model costs far more.** The same 342 million tokens sent to a general chat model, at $1 to $3 per million
  input tokens, would be $340 to $1,030, before output tokens, and its answers would still need parsing (I1).
- **The filings never leave Marlowe.** For data you cannot send to an outside service, a model you run yourself is
  the only option.

What Kev cannot do is replace Jev as the teacher. Kev learned from Jev's labels; it agrees with them on 88% of
filings. Jev made the labels once, for $14; Kev copies them as often as you like.
