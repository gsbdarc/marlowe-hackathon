# B3. Fine-tune on one Marlowe GPU

**Objective:** run your B2 fine-tune again on one H100 on Marlowe, and measure how much faster it trains than on the
Yens.
{: .fs-6 .fw-300 }

| | |
|---|---|
| Where | Marlowe, 1 H100 |
| Data | `train.jsonl` with Jev's soft labels: the same 512 filings as a B2 run on an A40 |
| Model | the same model as your B2 job, with the same settings |

Marlowe is a separate cluster from the Yens, with its own login, its own storage, and nodes of 8 H100 GPUs each.
Nothing you made on the Yens is there, so you set up once more before you train.

---

## Get onto Marlowe

Log in to Marlowe and make your own copy of this repository in the hackathon's project folder. Your Marlowe home
folder holds only 32 GB, so everything lives under `/scratch/m000106/gsb_hackathon/`:

```bash
ssh <sunet>@login.marlowe.stanford.edu
mkdir -p /scratch/m000106/gsb_hackathon/$USER
cd /scratch/m000106/gsb_hackathon/$USER
git clone https://github.com/gsbdarc/marlowe-hackathon.git
cd marlowe-hackathon
source env/marlowe.sh
```
{: .marlowe }

`source env/marlowe.sh` does on Marlowe what `source scripts/beginner/yens.sh` did on the Yens: it points `$WORK`,
`$KEV_HOME` and `$PY` at your folders here. Run it again, from your clone, whenever you open a new terminal.

Install Kev, as you did on the Yens. It takes about 3 minutes:

```bash
bash scripts/setup_kev.sh
```
{: .marlowe }

It ends with:

```
model ok: jaredpalmer/kev-4b@v1.0
model ok: Qwen/Qwen3.5-4B-Base@main
model ok: jaredpalmer/kev-27b@af0e6d551bdc2cc724f3e9d7a8bee1cd4fb8f7bf
tokenizer ok: Qwen/Qwen3.8-27B@1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0
Kev ready: /scratch/m000106/gsb_hackathon/<sunet>/kev/kev at 53cb0b5, Python 3.13.16
```
{: .output }

Put the room's W&B key in this clone too, so your run reaches the board, and put your SUNet ID in the job file, so
Slurm emails you when the job starts, ends or fails:

```bash
echo "WANDB_API_KEY=<the room's key>" > .env
sed -i "s/<sunet>/$USER/" slurm/marlowe/beginner/finetune_kev.slurm
```
{: .marlowe }

Then copy the training filings from the hackathon's shared, read-only data folder into your own:

```bash
mkdir -p $WORK/data
cp /scratch/m000106/gsb_hackathon/ceo-turnover/data/train.jsonl $WORK/data/
```
{: .marlowe }

## Run it: the same fine-tune on one H100

One Slurm job does all of it:

1. Slurm gives the job one H100 on a Marlowe node.
2. The job trains the same model as your B2 job, with the same settings, on the same 512 filings, in 64 steps of 8.
   It is the same work as a B2 run on an A40, so the times compare.
3. It prints the time per step, as your B2 job did.
4. It sends the loss to W&B, which is on the board.

It does not score the model. The training is the same as in B2, so only the speed changes.

{: .important }
> Use the **same settings as your B2 job**, so that the only difference is the GPU. If your B2 command was
> `LR=2e-4 sbatch slurm/yens/beginner/finetune_kev.slurm`, run `LR=2e-4 sbatch slurm/marlowe/beginner/finetune_kev.slurm`.
> Leave out any `-C GPU_MODEL:...`: every GPU on Marlowe is an H100.

```bash
mkdir -p logs
sbatch slurm/marlowe/beginner/finetune_kev.slurm
```
{: .marlowe }

`sbatch` prints the job's ID. `squeue --me` shows the job: `PD` while it waits for a GPU, `R` once it runs. Follow its
log:

```bash
tail -f logs/b3-finetune-1gpu-<jobid>.out
```
{: .marlowe }

Ctrl-C stops following; the job keeps running. The job runs on Marlowe's `preempt` partition: Slurm can stop it to
make room for a higher-priority job, and then starts it again.

## Compare with the Yens

The last lines of the log are the same table your B2 job printed. This is the one from a B2 run on an A40:

```
run              GPUs steps  s/step peak GPU GB epoch hours epoch GPU-hours
<jobid>             1    64    8.17        22.3        15.0            15.0
```
{: .output }

| Column | What it means |
|---|---|
| `GPUs` | how many GPUs shared the training: 1 here |
| `steps` | optimizer steps the run did; each step trains on 8 filings |
| `s/step` | seconds per step: the median step time, skipping the first 3, which are slower while things warm up |
| `peak GPU GB` | the most memory PyTorch used on the GPU: out of 48 GB on an A40, 80 GB on an H100 |
| `epoch hours` | how long one full pass over `train.jsonl` would take at this speed |
| `epoch GPU-hours` | what that full pass costs: hours × GPUs. It matters from B4, with more than one GPU |

To see your own B2 numbers, look at the end of your B2 log on the Yens:

```bash
tail -3 logs/ceo-finetune-<your B2 jobid>.out
```
{: .yens }

The H100 is a data-center GPU, a generation newer than the A40. Its tensor cores do bf16 arithmetic several times as
fast, and its memory moves data about five times as fast: 3.35 TB per second, against the A40's 696 GB.

<details class="quiz" markdown="1">
<summary><span class="qnum">1</span><span class="qtext">How many times faster is one step on the H100 than on the A40?</span></summary>

Divide the A40's `s/step` by the H100's. Both runs did the same 64 steps of 8 filings, so the difference is the GPU.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">2</span><span class="qtext">How long would a full pass over <code>train.jsonl</code> take on one H100?</span></summary>

`epoch hours`, in the last line of the log. Compare it with the A40's 15 hours from the B2 run above.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">3</span><span class="qtext">How much of the H100's memory did the training use? Is memory what limits you here?</span></summary>

`peak GPU GB`, out of 80. A 4B model with a LoRA adapter uses a fraction of it: what limits you is how fast the GPU
works through the steps, not whether the model fits. B4 adds GPUs to go faster.

</details>
