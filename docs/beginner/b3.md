# B3. Run it on Marlowe

**Objective:** run the exact training from B2 again, this time on **Marlowe**, Stanford's H100 cluster, and measure
how much faster a data-center GPU is. Everyone leaves the day having run a job on Marlowe; this is yours.
{: .fs-6 .fw-300 }

| | |
|---|---|
| Where | Marlowe, 1 H100 |
| Data | the same training filings as B2 |
| Model | the same Kev-4B fine-tune as B2, timed on an H100 instead of an A40 |
| Time | about 30 minutes |

Marlowe is a **separate cluster** from the Yens: its own login, its own storage, its own GPUs. Nothing you made on the
Yens is there, so you set up once more: the same steps as B1, on a new machine. Its GPUs are **H100s**, a generation
newer than the Yens A40 you have been using.

---

## Before you start

- Have your **B2 `s/step`** number ready (the timing line near the end of your B2 log). You compare against it here.
- **Open a second terminal window** for Marlowe and keep the Yens one open. Each window is logged in to one cluster;
  the prompt tells you which (`yen` or `login`). Running a Yens command on Marlowe, or the other way round, is the
  most common mix-up of the afternoon.

---

## Step 1: log in to Marlowe and get the code

The same as the Yens, at a different address. Your password does not show as you type, and Duo sends a push:

```bash
ssh <sunet>@login.marlowe.stanford.edu
```
{: .laptop }

Make your folder in Marlowe's scratch and get the code. Marlowe's scratch for this class is `/scratch/c001`, and your
folder in it is `/scratch/c001/users/<sunet>`. `mkdir -p` makes the folder, and does nothing if it already exists:

```bash
mkdir -p /scratch/c001/users/$USER
cd /scratch/c001/users/$USER
git clone https://github.com/gsbdarc/marlowe-hackathon.git
cd marlowe-hackathon
mkdir -p logs
source env/marlowe.sh
```
{: .marlowe }

Your Marlowe home folder holds only 32 GB, which is why everything goes in scratch, as on the Yens.

`source env/marlowe.sh` does on Marlowe what `source scripts/beginner/yens.sh` did on the Yens: it points this
terminal at Marlowe's shared data and prebuilt model. As on the Yens, run the `cd` and the `source` again whenever you
open a new terminal. Check the model is in place (a few seconds; there is nothing to install):

```bash
bash scripts/setup_kev.sh
```
{: .marlowe }

Put your SUNet ID into the job files, so Slurm emails you when a job starts and ends. `sed` edits a file from the
command line: this one replaces the text `<sunet>`{: .literal } in them with your ID (`$USER`):

```bash
sed -i "s/<sunet>/$USER/" slurm/marlowe/beginner/*.slurm
```
{: .marlowe .literal }

As on the Yens, your jobs find the room's W&B key by themselves. Only if this job's log starts with `W&B off`, put
the key in `.env` here too, the same way as in B1 (`.env` files do not travel between clusters).

That `sed` line also fills in the B4 job file, so you will not need it again.

## Step 2: submit the job

Marlowe's job file asks for a few things the Yens one did not. Look at its top:

```bash
head -14 slurm/marlowe/beginner/finetune.slurm
```
{: .marlowe }

| Line | What it asks for |
|---|---|
| `--account=marlowe-c001` | whose GPU time to charge. On Marlowe every job is charged to a **project**; this is the hackathon's |
| `--partition=batch` | the group of nodes to run on |
| `--gpus-per-node=1` | one H100 |
| `--time=00:20:00` | at most 20 minutes |
| `--mail-type`, `--mail-user` | email you when it starts, ends or fails |

The same command as B2, pointed at Marlowe's job file, with one more request on the command line.
`--reservation=GSB_Hackathon` asks for the nodes Marlowe set aside for this class today, so you are not waiting behind
the rest of Stanford:

```bash
sbatch --reservation=GSB_Hackathon slurm/marlowe/beginner/finetune.slurm
```
{: .marlowe }

Type the job ID into the box above the next command. Check the queue and follow the log, exactly as on the Yens:

```bash
squeue --me
tail -f logs/b3-finetune-1gpu-<jobid>.out
```
{: .marlowe }

If `tail` says `No such file or directory`, the job has not started yet, so there is no log: wait until `squeue --me`
shows it at `R`, then run the `tail` line again.

{: .note }
> If `squeue` shows your job pending (`PD`) for a while, it is waiting its turn for a GPU in the class's reserved
> nodes, the same as a busy queue on the Yens, and it will start on its own. You do not resubmit it. If it disappears
> from `squeue` without finishing, put up a 🟥.

The job trains the same model on the same filings as B2, so you are not looking for a new score (it does not score
the model at all). You are looking at the **speed**. The last lines print a table like this one:

```
run              GPUs steps  s/step peak GPU GB epoch hours epoch GPU-hours
<jobid>             1   152    3.19        22.2         5.8             5.8
```
{: .output }

That is a first run we did before the event; yours will be close. (A second run of the same job is faster: the
[challenge](#challenge-run-it-twice) shows why.)

| Column | What it means |
|---|---|
| `steps` | steps this job took: 152 steps of 8 filings, more than B2's 64, to fill the same 10 minutes |
| `s/step` | seconds per step, the speed you are comparing; each step trains on 8 filings on both GPUs. It is the typical step, leaving out the first 3, which are slow while things warm up |
| `peak GPU GB` | the most GPU memory the job used, out of the H100's 80 GB |
| `epoch hours` | how long one full pass over all the training filings would take at this speed |
| `epoch GPU-hours` | the same, times the number of GPUs: what a Marlowe project application asks you to estimate ([GPU-hours]({{ '/concepts/' | relative_url }}#gpu-hours)) |

## How much faster?

<details class="quiz" markdown="1">
<summary><span class="qnum">1</span><span class="qtext">How many times faster is one step on Marlowe's H100 than on the Yens A40?</span></summary>

Divide the A40's `s/step` from your B2 log (about 7.7) by the H100's from this log (about 3.2): about 2.4 times, and
nearly 3 once the H100 has done its one-time warm-up (see the challenge). The H100 is a generation newer than the A40:
its arithmetic units are faster, and its memory moves data about five times as fast. Each step trains on the same 8
filings on both GPUs, so the difference is purely the GPU.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">2</span><span class="qtext">A full pass over the training filings takes about 14 hours on the A40. How long on the H100? Is that fast enough?</span></summary>

`epoch hours` in your log: about 6. Two and a half times as fast is a real gain, and it is still most of a working day for
one pass, while real training often takes several passes. One GPU, however fast, only goes so far. The way past it is to
use many GPUs at once, which is what [B4]({{ '/beginner/b4/' | relative_url }}) does.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">3</span><span class="qtext">The H100 has 80 GB of memory, and the job used about 22. Could you use the rest?</span></summary>

Yes, by training on more filings at once, or by training more of the model's numbers. The Intermediate track does
both. For this job, the H100's memory is not what limits you: its speed is.

</details>

## Your decision: spend the speed on time, or on data?

A faster GPU gives you a choice. This job spent the H100's speed on **data**: in the same 10 minutes as B2, it trained
on 1,216 filings instead of 512. It could have spent it on **time** instead: the same 512 filings as B2, finished in
about 4 minutes. `FILINGS=512` in front of `sbatch` does that:

```bash
FILINGS=512 sbatch --reservation=GSB_Hackathon slurm/marlowe/beginner/finetune.slurm
```
{: .marlowe }

If the room picked a learning rate other than the default in B2, add it the same way, for example
`LR=2e-6 FILINGS=512 sbatch ...`. You do not have to run either: the decision here is about your own work.

<details class="quiz" markdown="1">
<summary><span class="qnum">4</span><span class="qtext">For your own project, which would you choose, and when would you choose the other?</span></summary>

Spend it on **data** when the model is not yet good enough: B2's challenge showed that more training filings still
help, even if each extra batch helps less. Spend it on **time** when the answer is already good enough and you are
going to run the job many times: trying settings, re-running with new data, or sharing GPUs with a group. Saving 6
minutes on one run hardly matters; saving it on 50 runs is a working day. Most research projects are in the second
case more often than they expect.

</details>

## Challenge: run it twice

Submit exactly the same job again, and compare how long each job took from start to finish:

```bash
sbatch --reservation=GSB_Hackathon slurm/marlowe/beginner/finetune.slurm
```
{: .marlowe }

```bash
tail -f logs/b3-finetune-1gpu-<jobid>.out
```
{: .marlowe data-job="second" data-job-label="Second job ID" }

When it has finished, `sacct` ("Slurm accounting") shows how long any of your jobs took. `Elapsed` is the time from
start to finish:

```bash
sacct -u $USER -n -X -S today --name b3-finetune-1gpu -o JobID,Elapsed,State
```
{: .marlowe }

<details class="quiz" markdown="1">
<summary><span class="qnum">5</span><span class="qtext">Same job, same GPU, same filings. Why is the second run faster?</span></summary>

The first time code runs on a new kind of GPU, it **compiles** small GPU programs (kernels) tuned for that GPU, and
saves them in your cache folder on scratch. The second run finds them there and skips that work. In our runs the
whole job took 13 minutes 38 seconds the first time and 9 minutes 51 seconds the second. `s/step` changes less (3.19
the first time, 2.75 the second), because it leaves out the first steps, where most of the compiling happens. It is a
one-time cost, worth knowing when you time a job: the first run on a new cluster always looks slower than the cluster
really is.

</details>
