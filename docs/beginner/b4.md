# B4. Many GPUs at once

**Objective:** label Item 5.02 filings with Kev-4B on several of Marlowe's H100s at once, next to the same job on one,
and measure what the extra GPUs buy you and what they cost. You decide how many GPUs to use; the room's choices
together show how labeling scales, all the way to every filing since 2004, 296,477 of them, in about 20 minutes.
{: .fs-6 .fw-300 }

| | |
|---|---|
| Where | Marlowe: 1 H100, and 2, 4 or 8 H100s (your choice) at the same time |
| Data | every Item 5.02 filing since 2004 with text: 296,477, no labels needed |
| Model | Kev-4B as released, the model you scored in B1 |
| Time | about 40 minutes: two 20-minute jobs that run side by side, and reading while they run |

---

## Before you start

You need B3 done: your clone on Marlowe, and the `sed` line from B3 run (it filled your SUNet ID into the B4 job file
too). In a new Marlowe terminal, set up first:

```bash
cd /scratch/c001/users/$USER/marlowe-hackathon
source env/marlowe.sh
```
{: .marlowe }

---

## One GPU, then several

So far every job has used one GPU. A Marlowe **node** is one computer with **8 H100s** in it. How do you get several
GPUs to work on one task?

For labeling, the answer is simple. Kev-4B fits easily on one GPU, so the job starts **one copy of the model on each
GPU**. The filings are dealt out like cards into **8 piles**, called **shards**: the first filing to pile 0, the second
to pile 1, and so on. Each GPU answers one pile. The GPUs never need to talk to each other; each one does exactly what
your one GPU did in B1, on its own pile.

```
296,477 filings ──► dealt into 8 piles ──► GPU 0: pile 0, 37,060 filings
                                           GPU 1: pile 1, 37,060 filings
                                           ...                               all at the same time
```

A job with 1 GPU labels pile 0. A job with 4 GPUs labels piles 0 to 3, and one with 8 labels all of them. Because the
cards were dealt in filing order, every pile is a spread of filings across all the years, so even one pile is a fair
sample of the whole collection. You will use that in B5.

---

## Your decision: how many GPUs?

Everyone runs two jobs side by side: the **1-GPU job**, the yardstick, and a second job with the number of GPUs you
choose:

| GPUs | Piles | Filings | What to expect |
|---|---|---|---|
| 2 | 0 to 1 | 74,120 | a quarter of a node: starts quickly |
| 4 | 0 to 3 | 148,240 | half a node |
| 8 | all 8 | 296,477 | a whole node: may wait for one to free up |

The class has **4 nodes, 32 H100s, for the whole room**, so a job that asks for 8 waits until a whole node is free,
while a 2-GPU job slips into the gaps. Spread the choices around your table, so the room has runs of all three.

<details class="quiz" markdown="1">
<summary><span class="qnum">1</span><span class="qtext">Predict before you run: your job does 2, 4 or 8 times the 1-GPU job's work. Will it take longer, the same time, or less?</span></summary>

About the same time. Each GPU has exactly one pile, the same size as the 1-GPU job's pile, and they all work at once.
So a job with N GPUs finishes N times the work in about the time one GPU takes for one pile. That is what "N times
faster" means here.

</details>

## Step 1: submit both jobs

One job file does both: `--gpus-per-node` on the command line sets how many GPUs, and the CPUs and memory scale with
it. Look at its top:

```bash
head -11 slurm/marlowe/beginner/label.slurm
```
{: .marlowe }

| Line | What it asks for |
|---|---|
| `--gpus-per-node=1` | one H100, unless you ask for more on the command line |
| `--cpus-per-gpu=8` | 8 CPU cores for each GPU |
| `--mem-per-gpu=64G` | 64 GB of ordinary memory (not GPU memory) for each GPU |

Submit the 1-GPU job:

```bash
sbatch --reservation=GSB_Hackathon slurm/marlowe/beginner/label.slurm
```
{: .marlowe }

and your choice. For 4 GPUs (put 2 or 8 instead of 4 if that is what you chose):

```bash
sbatch --reservation=GSB_Hackathon --gpus-per-node=4 slurm/marlowe/beginner/label.slurm
```
{: .marlowe }

Each prints a job ID. Type the 1-GPU job's into the first box below and the other's into the second. Then check the
queue:

```bash
squeue --me
```
{: .marlowe }

{: .note }
> If your bigger job sits at `PD` while the 1-GPU job runs, that is Slurm waiting for enough GPUs on one node. It will
> start; read the next section while it waits.

## Step 2: watch them work

Each job prints the progress of its first GPU. Follow the 1-GPU job. The first line saves its job ID in a shell
variable, `ONE`, for Step 3:

```bash
ONE=<jobid>
tail -f logs/b4-label-$ONE.out
```
{: .marlowe data-job="one" data-job-label="1-GPU job ID" }

If the first line answers `jobid: No such file or directory`, the box above it is empty: type the job ID into it and
copy the lines again. If `tail` says `No such file or directory` about the log, the job has not started yet: wait for
`R` in `squeue --me`.

Then, once it is running, your bigger job, saved as `MINE` (Ctrl-C stops one `tail` before you start the next):

```bash
MINE=<jobid>
tail -f logs/b4-label-$MINE.out
```
{: .marlowe data-job="mine" data-job-label="Your bigger job's ID" }

A running job looks like this:

```
8 Kev servers ready in 171 s on n01: jaredpalmer/kev-4b@v1.0
37,060 filings, 0 already answered, 37,060 to send at concurrency 64
  100/37,060  11.2 filings/s  failed 0
  ...
  37,000/37,060  38.5 filings/s  failed 0
```
{: .output }

First the job starts the models (the "servers") and waits for them to load, which takes 2 to 3 minutes. Then the
count climbs: that is GPU 0's pile. The rate starts slow and settles around 36 to 39 filings a second on each GPU.

You can watch every GPU at work. Each line of the GPU log is one GPU, every 5 seconds; look for one line per GPU with
the same time, all busy:

```bash
tail -8 logs/gpu-$MINE.csv
```
{: .marlowe }

## Step 3: compare the two

When **both** jobs have finished (`squeue --me` shows neither), add them up side by side:

```bash
$PY scripts/intermediate/shards.py $WORK/results/b4/$ONE $WORK/results/b4/$MINE
```
{: .marlowe }

Each job gets a row, with a line under it about the answers it saved. If a row says `no job-*.json`, that job is
still running, or the ID in `ONE` or `MINE` is wrong. If the rows are missing altogether, `ONE` and `MINE` are empty,
usually because this is a new terminal: set them again (`ONE=` followed by the 1-GPU job ID, `MINE=` followed by the
other) and run the line again.

```
job        GPUs  filings failed filings/s load s all hours GPU-hours  GPUs $  Jev $
<1-GPU>       1   37,060      0      36.1    135      2.28      2.28    6.84  14.38
<8-GPU>       8  296,477      0     306.4    171      0.27      2.15    6.45  14.38
```
{: .output }

That is a 1-GPU and an 8-GPU job from our runs before the event; yours will be close. Our runs of all four sizes:

| GPUs | filings/s | Times one GPU | all hours | GPU-hours |
|---|---|---|---|---|
| 1 | 36.1 | 1 | 2.28 | 2.28 |
| 2 | 78.4 | 2.2 | 1.05 | 2.10 |
| 4 | 156.3 | 4.3 | 0.53 | 2.11 |
| 8 | 306.4 | 8.5 | 0.27 | 2.15 |

| Column | What it means |
|---|---|
| `filings/s` | filings per second, all GPUs together |
| `load s` | seconds spent loading the model before labeling anything |
| `all hours` | how long labeling **all** 296,477 filings takes at this rate. For a job with fewer than 8 GPUs, that is its piles, then the next ones, until all 8 are done |
| `GPU-hours` | `all hours` times the number of GPUs: the GPU time you would be charged |
| `GPUs $` | those GPU-hours at $3 an hour, a typical price for an H100 |
| `Jev $` | what Jev, the hosted model, charges for the same filings |

Post your two rows in the 🧵 **B4** thread, then look at everyone else's: the room has now measured 1, 2, 4 and 8.

<details class="quiz" markdown="1">
<summary><span class="qnum">2</span><span class="qtext">How many times faster than one GPU was your job? Why not exactly 2, 4 or 8?</span></summary>

Divide your job's `filings/s` by the 1-GPU job's. In our runs it was 2.2 with 2 GPUs, 4.3 with 4 and 8.5 with 8. It is never exactly N, in either direction: the two jobs ran on different nodes, next to
other people's jobs, and one pile can hold slightly harder filings than another. Close to N is as good as it gets,
and you only get that because the GPUs never wait for each other.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">3</span><span class="qtext">Which costs more to label everything, 1 GPU or 8?</span></summary>

About the same: 2.28 against 2.15 GPU-hours in our runs. 8 GPUs for a quarter of an hour cost about what 1 GPU costs
for 2 hours. More GPUs buy you **time**, almost for free. Look at the room's runs: `GPU-hours` hardly moves between 1,
2, 4 and 8, while `all hours` falls with every doubling. Where there is an extra on the bigger jobs, it is loading:
every GPU spends its first minutes loading the model and labeling nothing.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">4</span><span class="qtext">If more GPUs cost the same, why would anyone choose fewer?</span></summary>

Because of the queue. A job only starts when all the GPUs it asks for are free on one node at once, so a 2-GPU job
can start in a gap while an 8-GPU job waits for a whole node. If the wait is longer than the time the extra GPUs save,
fewer GPUs finish first. On a busy cluster, the fastest job on paper is not always the fastest one in practice.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">5</span><span class="qtext">Kev on Marlowe or Jev: which is cheaper?</span></summary>

Kev, at about $6.50 against about $14 for Jev, if you rented the GPUs from a cloud at $3 an hour. On Marlowe there is
no bill at all: your project's allocation of GPU-hours covers it. And you keep the model, the data never leaves
Stanford, and you can run it again tomorrow for the same price. Cheaper is not the same as as good, though: Kev-4B as
released agrees with Jev on 88% of filings and 59% of CEO changes, which is why B2 trained it. B5 shows what that gap
does to a research result.

</details>

## What the jobs produced

| File | What is in it |
|---|---|
| `logs/b4-label-<jobid>.out` | each job's log |
| `$WORK/results/b4/<jobid>/shard-<n>.jsonl` | Kev-4B's answers, one line per filing, one file per pile |
| `$WORK/results/b4/<jobid>/shard-<n>.log`, `shard-<n>_summary.json` | each GPU's own progress log, and its speed and count, which `shards.py` reads |
| `$WORK/results/b4/<jobid>/job-0.json` | the job's GPUs and how long the models took to load, which `shards.py` also reads |
| `logs/kev-server-<jobid>-gpu<n>.log` | each GPU's model server: look here if the job stops early |

Every one of those lines is a labeled filing. Look at one:

```bash
head -1 $WORK/results/b4/$MINE/shard-0.jsonl
```
{: .marlowe }

You now hold Kev-4B's answers for a share of every Item 5.02 filing since 2004, or all of them, made in about 20
minutes on hardware Stanford runs. Keep `ONE` and `MINE`: B5 turns these answers into a finding.

## Challenge: plan your own project

No job to run for this one: a pencil, or a calculator, and the table from Step 3. This is the arithmetic a Marlowe
project application asks for.

Say your research needs **3 million** documents labeled, about ten times this collection, with a model like Kev-4B.

<details class="quiz" markdown="1">
<summary><span class="qnum">6</span><span class="qtext">How many GPU-hours, and how long on one node?</span></summary>

Ten times the 8-GPU job: about 22 GPU-hours, and about 2.7 hours on one node (0.27 hours × 10). On one GPU it would be
about 23 hours. Same GPU-hours either way; the node gets you the answer the same afternoon.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">7</span><span class="qtext">You want it in under an hour. How many nodes?</span></summary>

Three: 2.7 hours ÷ 3 nodes is 0.9 hours. Because the GPUs never talk to each other, more nodes split the piles further
and the speed keeps scaling. The Intermediate track's [I5]({{ '/intermediate/i5/' | relative_url }}) shows how to run
one job across several nodes.

</details>
