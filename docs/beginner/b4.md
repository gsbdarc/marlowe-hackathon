# B4. Fine-tune on a full node

**Objective:** run B3's full fine-tune on all 8 H100s of one Marlowe node, and measure how much faster it trains and
what it costs, compared with one GPU.
{: .fs-6 .fw-300 }

| | |
|---|---|
| Where | Marlowe, 8 H100s (one node) |
| Data | `train.jsonl` with Jev's soft labels |
| Model | Kev-4B with every weight trained, as in B3 Part 2 |

You need B3 done, both parts: the full fine-tune on one H100 made `$WORK/kev-4b-full`, which this job starts from,
and its time per step is what you compare with.

---

## Why one GPU is slow, and what 8 change

In B3 Part 2, one H100 trained all 4.2 billion weights. A full fine-tune needs 67 GB for the weights, gradients,
master copies and optimizer averages, so Kev kept 50 GB of it in the node's memory and streamed it over to the GPU
every step. The GPU spent part of each step waiting for that traffic.

With 8 GPUs, two things split 8 ways:

- **The memory.** **FSDP2** (Fully Sharded Data Parallel, PyTorch's second version of it) gives each GPU 1/8 of every
  weight, gradient, master copy and average: about 8.4 GB each instead of 67 GB in one place. Everything fits on the
  GPUs, so nothing streams to the node's memory.
- **The work.** Each step's 16 filings are dealt out, 2 to each GPU. The 8 GPUs work on their filings at the same time.

<details markdown="1">
<summary>How 8 GPUs train one model</summary>

`torchrun` starts 8 copies of Kev's trainer, one per GPU. They are the same program, each told its number (its
*rank*, 0 to 7), and they talk to each other over **NVLink**, the links that join the 8 GPUs in a Marlowe node at
900 GB per second.

Each step, for every layer of the model in turn:

1. **Gather.** Each GPU holds only its 1/8 of the layer's weights. The 8 GPUs send each other their pieces, so each has
   the whole layer for a moment.
2. **Compute.** Each GPU runs its own 2 filings through the layer, then frees the gathered weights and keeps only its
   own 1/8 again.
3. **Share the gradients.** On the way back through the model, each GPU has gradients from its own 2 filings, for the
   whole layer. The GPUs add them up and split the sum, so each ends with the gradient over all 16 filings, for its
   1/8 of the weights.

Then each GPU updates its own 1/8 of the weights with AdamW. The 8 GPUs used the same gradient, so the 8 pieces stay
one model, trained on the same 16 filings a step as on one GPU.

Only rank 0 writes the log, so `logs/b4-full-8gpu-<jobid>.out` looks like a one-GPU log.

</details>

## Run it

The job asks Slurm for a whole node (`--gpus-per-node=8 --exclusive --mem=0`), then runs the same trainer as B3 under
`torchrun`, with the same 100 steps of 16 filings:

```bash
sed -i "s/<sunet>/$USER/" slurm/marlowe/beginner/full_ft_8gpu.slurm
sbatch slurm/marlowe/beginner/full_ft_8gpu.slurm
tail -f logs/b4-full-8gpu-<jobid>.out
```
{: .marlowe }

A whole node is harder to get than one GPU: the job waits in the queue until no one else is using any of the node's 8
GPUs, so it can take longer to start. While it runs, `logs/gpu-<jobid>.csv` shows all 8 GPUs' memory and utilization.

The settings are the same as B3 Part 2's, set before `sbatch`:

| Setting | Default | Change it with |
|---|---|---|
| Learning rate | 2e-5 | `LR=1e-5` |
| Filings per step, across all 8 GPUs | 16 | `RECORDS_PER_STEP=32` (a multiple of 8) |
| Steps | 100 | `STEPS=50` (at least 20) |

## Compare with one GPU

Print both runs side by side:

```bash
$PY scripts/step_times.py $WORK/runs/b3-full/<B3 jobid> $WORK/runs/b4/<jobid>
```
{: .marlowe }

```
run              GPUs steps  s/step peak GPU GB epoch hours epoch GPU-hours
<B3 jobid>          1   100    9.33        19.5         8.5             8.5
<jobid>             8   100    1.01        12.8         0.9             7.4
```
{: .output }

These are the two runs we did before the event. The 100 steps took 17 minutes on one GPU and under 2 on eight; the
whole job, with loading the model and saving it, took 20 minutes and 5½.

<details class="quiz" markdown="1">
<summary><span class="qnum">1</span><span class="qtext">How many times faster is a step on 8 GPUs? How can it be more than 8?</span></summary>

9.33 ÷ 1.01: about 9.2 times. You would expect at most 8, since the GPUs also spend time gathering weights and adding
up gradients, and each step waits for the slowest GPU.

The extra comes from the one-GPU run, not the eight. On one GPU, the update after each step ran in the node's memory,
on the CPU, with every gradient and weight crossing between the GPU and the node: 1.5 seconds of every 9.3-second step.
On 8 GPUs every weight's master copy and averages fit on a GPU, so the update runs there, in 0.05 seconds. The rest of
the step, running the filings through the model, got about 8 times faster, as you would expect. Splitting the work
8 ways gave 8 times; getting everything onto the GPUs gave the rest.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">2</span><span class="qtext">Which run costs more?</span></summary>

`epoch GPU-hours`: the hours one pass over `train.jsonl` takes, times the GPUs. Marlowe charges by GPU-hours. Here 8
GPUs cost *less*, 7.4 GPU-hours against 8.5, because they were more than 8 times as fast.

That is unusual. When the one-GPU run does not have to spill into the node's memory, 8 GPUs are less than 8 times as
fast, and the same training costs more on 8. The Advanced track's 27B full fine-tune, for example, is 5 times as fast
on 8 GPUs and costs about 60% more GPU-hours.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">3</span><span class="qtext">How much memory did each GPU use?</span></summary>

12.8 GB on each GPU, against 19.5 GB on one. Each GPU holds 1/8 of the 67 GB, about 8.4 GB, plus the filings it is
working on and the one layer it has gathered. Almost 70 GB of each H100 sat unused: a model about 6 times bigger would
still fit on this node.

</details>

## More GPUs: worth it?

| | One GPU | 8 GPUs, FSDP2 |
|---|---|---|
| Time to a result | slow | here 9 times faster |
| Cost (GPU-hours) | usually lowest | usually higher, since the GPUs spend time talking to each other; here lower, because one GPU had to spill into the node's memory |
| Biggest model it can train | what fits in one GPU (or, as here, one GPU plus the node's memory) | 8 times more |
| Getting a GPU | quick: any free GPU on any node | slower: a whole node has to be free |
| What can go wrong | one program | 8 programs that must stay in step: one failing stops all 8 |

**Use more GPUs when** time matters more than GPU-hours, or when the model does not fit on one GPU at all. A full
fine-tune of a 27B model needs about 430 GB; no single GPU has that, so it has to be split.

**Stay on one GPU when** the model fits and you can wait. A LoRA run on Qwen 4B peaks at 22 GB: splitting it 8 ways
saves no memory that matters, and the GPUs would spend much of each step talking. To use 8 GPUs for small runs, it
usually pays more to run 8 different experiments side by side, one per GPU, than one experiment across all 8.

## Going further: LoRA on 4 and 8 GPUs

FSDP2 is one way to train on several GPUs. The other common one is **DDP** (Distributed Data Parallel): every GPU keeps
a **whole copy** of the model, trains on its share of each step's filings, and the GPUs add up their gradients once
per step. Nothing is sharded, so nothing is gathered layer by layer.

| | DDP | FSDP2 |
|---|---|---|
| Each GPU holds | the whole model, its gradients and optimizer state | 1/8 of each |
| Talking each step | add up the gradients, once | gather every layer's weights, then share its gradients |
| Full fine-tune of Kev-4B, per GPU | 67 GB before activations: barely fits, if at all, in an H100's 80 | 8.4 GB |
| LoRA on Kev-4B, per GPU | about 22 GB, as on one GPU | little saved: the frozen weights are most of it |

So full fine-tunes shard, and LoRA, whose trainable adapter is tiny, is DDP's natural case. Kev's trainer runs LoRA on
one GPU only; `scripts/beginner/kev-lora-ddp.patch` adds the data-parallel path. The jobs below apply it, the first time, to a
second checkout of Kev, `$KEV_HOME/kev-lora-ddp`, and leave your own Kev as it is.

All three train the same 1,600 filings as B3 Part 2 and this page's full fine-tunes: 100 steps of 16, at lr 2e-5. On 4
GPUs each takes 4 filings a step; on 8, 2.

```bash
sed -i "s/<sunet>/$USER/" slurm/marlowe/beginner/lora_*gpu.slurm slurm/marlowe/beginner/score_test.slurm
sbatch slurm/marlowe/beginner/lora_1gpu.slurm      # 1 H100
sbatch slurm/marlowe/beginner/lora_4gpu.slurm      # 4 H100s, half a node
sbatch slurm/marlowe/beginner/lora_8gpu.slurm      # 8 H100s, a whole node
```
{: .marlowe }

Each run is `$WORK/runs/lora-ddp/<jobid>`. Compare their speed with the full fine-tunes:

```bash
$PY scripts/step_times.py $WORK/runs/lora-ddp/<1-GPU jobid> $WORK/runs/lora-ddp/<4-GPU jobid> $WORK/runs/lora-ddp/<8-GPU jobid>
```
{: .marlowe }

### Score every method on the same test filings

Speed is half the story. To see whether the methods also learn the same thing, score all of them on the same 1,000 test
filings from B1. `score_test.slurm` loads each run in turn on one H100, labels the test filings, and prints one table:

```bash
RUNS="kev-4b=jaredpalmer/kev-4b@v1.0
      lora-1gpu=$WORK/runs/lora-ddp/<jobid> lora-4gpu=$WORK/runs/lora-ddp/<jobid> lora-8gpu=$WORK/runs/lora-ddp/<jobid>
      full-1gpu=$WORK/runs/b3-full/<jobid> full-8gpu=$WORK/runs/b4/<jobid>" \
  sbatch slurm/marlowe/beginner/score_test.slurm
```
{: .marlowe }

The first time, it builds `valid` and `test1000` in `$WORK/data` from Jev's labels (the same filings as B1's), leaving
`train.jsonl` as it is. A run it has already labeled is not labeled again, so you can add runs and submit it again.

<details class="quiz" markdown="1">
<summary><span class="qnum">4</span><span class="qtext">Should LoRA on 1, 4 and 8 GPUs score the same?</span></summary>

Nearly. Each step sees the same 16 filings and makes the same update on 1, 4 or 8 GPUs: the GPUs only split the work.
The sums are added in a different order, so the numbers differ in the last digits, and over 100 steps the runs can
drift apart a little. A gap much bigger than the gap between two 1-GPU runs with different seeds would mean something
is wrong.

LoRA against the full fine-tune is a real difference: the full fine-tune changes every weight, LoRA a small adapter.

</details>
