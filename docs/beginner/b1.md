# B1. Your first GPU job

**Objective:** run your first job on a shared GPU. You take Kev-4B, a small open model, exactly as it was released,
and measure how often it agrees with a large model called Jev on 1,000 real filings. Along the way you meet the four
things every cluster job uses: logging in, scratch storage, a GPU, and Slurm.
{: .fs-6 .fw-300 }

| | |
|---|---|
| Where | Yens, 1 GPU |
| Data | 1,000 test filings, already prepared for you |
| Model | [Kev-4B](https://huggingface.co/jaredpalmer/kev-4b) as released, no training from you |
| Time | about 30 minutes, most of it reading while the job runs |

---

## Before you start

You need three things. If any is missing, put up a 🟥 red sticky now and someone will come over.

- **A terminal.** On a Mac, open the **Terminal** app (press Cmd-Space and type "Terminal"). On Windows, open
  **PowerShell** from the Start menu. A terminal is a window where you type commands instead of clicking.
- **Your SUNet ID and password**, and your phone for the **Duo** push that Stanford logins ask for.
- **Your SUNet ID in this page's sidebar.** Type it into the box on the left. Every command on this site that needs
  your ID then fills it in for you, so you can copy commands exactly as they appear.

How to copy a command: hover over a grey box and click the copy icon in its corner, then paste it into the terminal
(Cmd-V on a Mac, right-click in PowerShell) and press Enter. Run the commands one box at a time, top to bottom.

## What you are about to do, in plain terms

A company tells the public its CEO is leaving by filing a short document with the SEC. There are hundreds of
thousands of these. A large hosted model, **Jev**, has read every one and answered three questions about each: what
happens to the CEO, why, and whether it was announced ahead of time. Jev is powerful, but it runs on someone else's
servers and costs money for every document.

**Kev-4B** is a small open model, small enough to run on one GPU that you control
([Key Ideas]({{ '/concepts/' | relative_url }}) says more about Jev and Kev). Out of the box it already agrees with
Jev most of the time. In B1 you measure exactly how often. In [B2]({{ '/beginner/b2/' | relative_url }}) you train it
to do better. That is the whole arc of the day: replace an expensive model you rent with a small one you own.

You do not need to understand the model to run this. You need to get one job onto a GPU and read what it prints.

---

## Four words you will use all day

A **cluster** is a room full of computers (called **nodes**) that many people share. You do not sit at one; you send
it work, and it runs the work when a machine is free. Four ideas cover almost everything:

| Word | What it means |
|---|---|
| **Login node** | the one computer you connect to and type on. It is for editing files and submitting jobs, not for heavy work, because everyone shares it. |
| **Scratch** | a big shared disk that every node can see. Your files go here so that whichever GPU runs your job can read them. |
| **GPU** | a graphics processor. Models run on GPUs because a GPU does the same simple arithmetic on thousands of numbers at once, which is exactly what a model is made of. The login node has none; the GPU nodes do. |
| **Slurm** | the program that hands out GPUs. You do not pick a machine yourself. You hand Slurm a small script that says "run this, I need one GPU", and it finds a free GPU, runs your job there, and saves what it prints. |

The Yens is Stanford GSB's cluster, and where you start. [Marlowe]({{ '/beginner/b3/' | relative_url }}) is a bigger
one you reach in B3.

## Step 1: log in and get the code

You connect to the login node with **SSH**, a command that opens a secure terminal on another computer:

```bash
ssh <sunet>@yen.stanford.edu
```
{: .laptop }

This is the one command you type on your own laptop. Type your password when asked. **Nothing appears as you type it**, not even dots: that is normal, so type it and press
Enter. Then approve the Duo push on your phone. The first time, SSH may also ask
`Are you sure you want to continue connecting (yes/no)?`: type `yes` and press Enter.

When the prompt changes to something like `<sunet>@yen1:~$`, you are typing on the Yens login node (the Yens call
these **interactive Yen nodes**), not your laptop.
Get your own copy of the hackathon's files and step into it:

```bash
cd /scratch/users/$USER
git clone https://github.com/gsbdarc/marlowe-hackathon.git
cd marlowe-hackathon
mkdir -p logs
```
{: .yens }

`/scratch/users/$USER` is your folder in scratch; `$USER` is your SUNet ID, filled in by the shell. `git clone`
downloads the files, and `cd` ("change directory") steps into them. `mkdir -p logs` makes the folder your jobs write
their logs to: Slurm will not make it for you. **Every command on this page runs from this folder.** If you are ever
unsure where you are, `pwd` prints it.

Scratch is for working files: it is not backed up, and files older than 90 days are deleted. That is fine for today.
Anything you want to keep afterwards belongs in a project space
([storage on the Yens](https://rcpedia.stanford.edu/_user_guide/storage/)).

Now set up your terminal and check the model is in place. The first line points this terminal at the shared data and
the prebuilt model; the second checks the model is there (a few seconds):

```bash
source scripts/beginner/yens.sh
bash scripts/setup_kev.sh
```
{: .yens }

It should end with `model ok:` lines and `Kev ready:`.

{: .important }
> `source scripts/beginner/yens.sh` lasts only as long as this terminal window. Whenever you open a new terminal (or
> log in again), run `cd /scratch/users/$USER/marlowe-hackathon` and then `source scripts/beginner/yens.sh` before
> anything else.

{: .note }
> **Your result goes on the room's screen by itself.** The front of the room shows a live board of everyone's runs,
> made with Weights & Biases (W&B). Your jobs find the room's W&B key in a shared file, so there is nothing to set up.
> If a job's log starts with `W&B off`, it could not read that file: put up a 🟥 red sticky, and whoever comes over
> will give you the key. Put it in a file called `.env` at the top of your clone, replacing `<the room's key>` and
> keeping the quotes:
>
> ```bash
> echo "WANDB_API_KEY=<the room's key>" > .env
> ```
> Either way the job runs and prints your score; without the key it just does not appear on the screen.

## Step 2: submit the job

The job is a short script, `slurm/yens/beginner/score.slurm`. Its top lines, the ones starting `#SBATCH`, are its
request to Slurm. It is worth reading them once:

```bash
head -9 slurm/yens/beginner/score.slurm
```
{: .yens }

| Line | What it asks Slurm for |
|---|---|
| `-J ceo-score` | a name for the job, so you can spot it in the queue |
| `-p gpu` | the **partition**: the group of nodes to run on, here the Yens GPU nodes |
| `-G 1` | one GPU |
| `-C GPU_MODEL:A40` | a particular kind of GPU, an NVIDIA A40 |
| `-c 8`, `--mem=32G` | 8 CPU cores and 32 GB of ordinary memory to go with the GPU |
| `-t 00:30:00` | at most 30 minutes; Slurm stops the job if it runs longer |
| `-o logs/%x-%j.out` | where to save what the job prints: `%x` becomes the job name and `%j` the job ID |

Below those lines is ordinary shell: start the model, send it the filings, score the answers.

### Your choice: which GPU

You make one decision before you submit: which kind of GPU to ask for. The Yens have two kinds you can use today:

| | NVIDIA A40 (the default) | NVIDIA H200 |
|---|---|---|
| Released | 2020 | 2024 |
| GPU memory | 48 GB | 141 GB |
| How many the room shares | 4 | 2 |

The H200 is newer and bigger, but the whole room shares two of them, so a job that asks for one may wait in the queue
while A40s sit free. Kev-4B needs about 10 GB, so it fits on either. **Before you submit, write down your
prediction:** will your choice change how fast the job runs? Will it change the scores?

One command hands Slurm the job. `sbatch` means "submit this script as a batch job", and
`--reservation=hackathon` asks for the GPUs set aside for this class today, so you are not waiting behind the rest of
the GSB. Run **one** of these two. For the A40, the job file as it is:

```bash
sbatch --reservation=hackathon slurm/yens/beginner/score.slurm
```
{: .yens }

For the H200, add `-C GPU_MODEL:H200`. An option given to `sbatch` on the command line replaces the matching `#SBATCH`
line in the file, so you do not edit the file:

```bash
sbatch --reservation=hackathon -C GPU_MODEL:H200 slurm/yens/beginner/score.slurm
```
{: .yens }

Slurm prints a number, the **job ID**, for example `Submitted batch job 12345678`. That is how you refer to your job.
**Type it into the "Job ID" box above the `tail` command in Step 3 below**; the commands after it then fill it in.

Your job is now in the **queue**. Slurm runs it as soon as a GPU is free, which is usually seconds but can be a few
minutes if the room is busy. See where it is:

```bash
squeue --me
```
{: .yens }

```
     JOBID PARTITION     NAME     USER ST       TIME  NODES NODELIST(REASON)
  12345678       gpu ceo-scor  <sunet>  R       0:12      1 yen-gpu-1
```
{: .output }

`ST` is the status: `PD` means pending (waiting for a GPU), `R` means running. When the job finishes, it drops off the
list. Run `squeue --me` again any time to check.

{: .important }
> You do not wait at the screen for it. The job runs on its own on a GPU node and saves everything it prints to a
> file, whether or not you are watching. You could close your laptop and it would keep going.

## Step 3: watch it work

Everything the job prints goes to a log file named after the job, in the `logs/` folder. Follow it live with
`tail -f` ("show me the end of the file, and keep showing new lines as they appear"):

```bash
tail -f logs/ceo-score-<jobid>.out
```
{: .yens }

If `tail` says `No such file or directory`, the job has not started yet, so there is no log: wait until `squeue --me`
shows it at `R`, then run the `tail` line again.

You will see the model load (about a minute), then a count climbing as it answers the 1,000 filings, then a table of
scores. Press **Ctrl-C** to stop following. That stops `tail`, not the job.

Near the end of a finished run is the score table (a breakdown by answer follows it):

```
             run  answered  status_agree_weighted  status_agree_on_ceo_changes  ceo_change_f1  ...
12345678.jsonl      1000                  0.884                        0.587          0.843  ...
```
{: .output }

Read that line left to right: the model answered all 1,000 filings, and it agreed with Jev **88% of the time
overall** and **59% of the time on the filings where the CEO actually changes**. Those two numbers are your B1
result. The CEO-change number is the hard one, and the one you push up in B2.

{: .note }
> **Why two numbers?** Most filings, about seven in eight, are *not* about the CEO at all: they report a new director,
> a CFO leaving, a pay change. Agreeing on those is easy, so the 88% is mostly the easy cases. The 59% is how well
> Kev-4B does on the filings that matter: the real CEO changes. That gap is the point of the day.

## When something goes wrong

| What you see | What it means | What to do |
|---|---|---|
| `Permission denied` when logging in | wrong password, or Duo not approved | try again slowly; the password does not show as you type |
| `sbatch: command not found` | you are typing on your laptop, not the Yens | log in first: `ssh <sunet>@yen.stanford.edu` |
| The job finished but `logs/ceo-score-<jobid>.out` does not exist | the `logs` folder was missing when you submitted | `mkdir -p logs`, then submit again |
| `No such file or directory` | you are not in your clone | `cd /scratch/users/$USER/marlowe-hackathon` |
| `$WORK` or `$PY` is empty, or `python: not found` | this terminal has not been set up | `source scripts/beginner/yens.sh` |
| `squeue` shows `PD` for a long time | every A40 is busy | wait; the reason in brackets says why. Ask if it is over 10 minutes |
| The job vanished from `squeue` but the log has no score table | it stopped early | read the end of the log, then `logs/kev-server-<jobid>.log`, and put up a 🟥 |

[Reference]({{ '/reference/' | relative_url }}#when-something-goes-wrong) has more of these, and the Slurm commands
in one place. To cancel a job you submitted by mistake: `scancel` followed by its job ID.

## What the job produced

Besides the log, the job saved its answers and scores in your folder:

| File | What is in it |
|---|---|
| `logs/ceo-score-<jobid>.out` | the log you just read |
| `logs/kev-server-<jobid>.log` | the model server's own log: look here if the job stops early |
| `logs/gpu-<jobid>.csv` | how busy the GPU was and how much of its memory was used, every 5 seconds |
| `$WORK/results/b1/<jobid>.jsonl` | Kev-4B's answer for each of the 1,000 filings |
| `$WORK/results/b1/<jobid>_scores.json` | the scores, with a breakdown by answer |

`$WORK` is your working folder in scratch, `/scratch/users/<sunet>/ceo-turnover`. Look at how hard the GPU worked:

```bash
tail -5 logs/gpu-<jobid>.csv
```
{: .yens }

The columns are the time, the GPU's name, how busy it was (as a percentage), and how much of its memory was in use.

<details class="quiz" markdown="1">
<summary><span class="qnum">1</span><span class="qtext">Your job ran on a GPU node, but you typed the command on the login node. How did the GPU node find your files?</span></summary>

Through **scratch**. Your clone lives in `/scratch/users/<sunet>`, and scratch is one disk that every node sees: the
login node where you typed `sbatch`, and the GPU node where the job ran. That is why there was nothing to copy: you
submit from one machine, and the job reads the same files from another.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">2</span><span class="qtext">You chose the kind of GPU. Who chose the GPU itself, and where?</span></summary>

You chose the *kind*: `#SBATCH -C GPU_MODEL:A40` in the job file, or `-C GPU_MODEL:H200` on the command line. Slurm
chose *which one*: it found a free GPU of that kind on some GPU node and ran your job there. `squeue` showed the node's
name under `NODELIST`.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">3</span><span class="qtext">Everyone in the room ran the same model on the same 1,000 filings. Will everyone get exactly the same score?</span></summary>

Very nearly. The filings and the model are the same, but a GPU adds up numbers in a slightly different order from run
to run, which can flip an answer that was a near tie. Expect the same numbers to two decimal places, sometimes three.

</details>

## Was your prediction right?

Compare your run with one on the other kind of GPU: from the board, from a neighbour, or from the B1 thread.

<details class="quiz" markdown="1">
<summary><span class="qnum">4</span><span class="qtext">Did the score change between the A40 and the H200? Did the speed?</span></summary>

The scores are the same, or within a hair: it is the same model answering the same filings, and a different GPU does
not make a model smarter or dumber. The `filings_per_second` column is what changes: about 20 on the H200 against about
6.4 on the A40, three times as fast, and the whole job took under 3 minutes instead of 5 and a half. Speed and quality
are separate questions, and choosing a GPU changes only the first.

</details>

<details class="quiz" markdown="1">
<summary><span class="qnum">5</span><span class="qtext">For your own research: you have 50,000 documents to label with a model like this one. How long on each GPU, and which would you ask for?</span></summary>

At 6.4 filings a second, an A40 takes about 2 hours 10 minutes; at 20 a second, an H200 takes about 40 minutes. Either
finishes the same afternoon, and an A40 you can get now may beat an H200 you wait an hour for. The faster GPU matters
when the job is long enough that its speed outweighs the wait, or when you will run it many times. There is no single
right answer: it depends on the queue, which is why `squeue` is worth a look before you choose.

</details>
